## P1: system map

The integration boundary has four authorities:

1. `package.json` and `bun.lock` own the exact installed package versions and
   registry integrity. Both ArchContext packages are production dependencies,
   not sibling-checkout or `file:` fallbacks.
2. `.ai/harness/policy.json`, the scaffold helpers, and
   `src/core/architecture/projection.ts` own the required product version used
   by initialized repositories and the provider handshake.
3. `src/effects/architecture/archctx-provider.ts` owns package-local binary
   resolution, compatible Node selection, capabilities validation, and
   projection execution. The authority path remains
   `runArchitectureProjection -> assertExpectedSnapshot -> consumeArchitectureRefreshSignals`.
4. `scripts/axr5-archctx-clean-room.ts` and
   `scripts/axr7-consumer-e2e.ts` own the producer-package and installed-consumer
   readbacks. Unit tests cover the provider state machine and durable queue;
   AXR7 crosses the real package-local CLI, HTTP-loopback daemon, CodeGraph
   1.5.0, Stop hook, durable receipt, and retry boundary.

This cut does not change `projection-result/v2`, `projection-protocol-v2`, or
the receipt schema. It also does not add a version fallback or permit PATH to
override package-local ArchContext.

## P3: decision rationale

The smallest coherent consumer change is an exact pin plus one runtime-floor
alignment. Keeping repo-harness at Node `>=24 <26` would make its install
contract stricter than the managed ArchContext closure and would leave the
required Node 22.22 provider path unrepresentable at the package boundary.
Changing repo-harness to `>=22.22 <26` preserves one source of truth for the
managed runtime while still failing closed below 22.22 and at Node 26.

At 10x repository size the first pressure remains projection/CodeGraph work,
not version selection: the provider is still one bounded package-local daemon
operation and the durable queue still coalesces source paths before spawning.
No new dependency, compatibility layer, or alternate runtime authority was
introduced.
