# Active adoption provider accounting and terminal proofs

> Historical record. Campaign execution moved to the existing Bot skills on 2026-10-04. Use [repo-harness](../../SKILL.md) to dispatch and collect work through Herdr/OAR. Use [repo-harness-product](../../assets/skills/repo-harness-product/SKILL.md) for planning and [repo-harness-check](../../assets/skill-commands/repo-harness-check/SKILL.md) for scope and verification. repo-harness has no campaign runtime.

The accepted shadow package at ce5e42d3 retains strict terminal freshness: `readCampaignAuthoringBudgetTerminal` and `verifyCampaignAuthoringBudgetTerminal` require the terminal's digest to equal the current complete ledger. Shadow completes its final observation step and seals under one run lock. A later GitHub read makes that old terminal stale, including on shadow replay.

Active adoption has a different ordering requirement: observe, seal authoring, then observe again for source drift before publication. Every actual GitHub identity/page invocation now enters the existing campaign provider executor, with admission before I/O and returned evidence before usage. Unresolved outcomes keep their reservation and prevent another invocation. The campaign ledger remains the only counting authority.

`readCampaignAuthoringReadonlyContinuation` and `verifyCampaignAuthoringReadonlyContinuation` explicitly prove a historical seal plus its current readonly continuation. Their result contains the original terminal, current ledger digest and subsequent completion event digests. They do not rewrite the terminal or claim its historical digest equals the current ledger. The sealed digest must match exactly one validated ledger prefix. Current authorization, budget and authoring evidence remain exact; the prefix and current state must be quiescent. Successors may only contain same-group, same-intent GitHub reads and their completed controller steps. Mutations, challenge, generic execution, unrelated groups and unresolved work are rejected.

Active adoption persists the continuation beside its adoption evidence. Publication recovery validates the seal and current continuation, performs a fresh budgeted observation, compares source revisions and validates continuation again before publication. Durable observation evidence can complete interrupted step bookkeeping; it is never substituted for the recovery invocation's fresh observation. A fault-injection regression reproduced the former ordering error: completion persistence failed after observation evidence was durable, and the next invocation rejected the active step before reaching its recovery path. Recovery now completes only its own exactly bound observation evidence before verification.

This package does not fix Connector exact-revision proof, complete BRC9's acquisition/repair/transient requirements, or activate later lifecycle packages. The BRC6a readback boundary remains independently owned. No full-suite or final acceptance claim follows from the focused development results.

The implementation adds no dependency or second store. Private observation evidence uses the existing immutable planning-record store. The explicit proof APIs separate two real consumers with different invariants; both fold the same authoritative ledger. The historical-prefix scan is linear in ledger size, as is the existing validation read. At higher load the existing single active step and unresolved-reservation constraints continue to serialize effects.
