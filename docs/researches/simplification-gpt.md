我的结论是：**这个项目确实应该做一轮明显的简化，而且不应只是缩短提示词、再加一个“轻量模式”，而应改变 harness 介入工作的方式。**

建议把它从：

> 约束 Agent 应该如何拆任务、如何写代码、如何证明每一步合规的流程系统

收敛为：

> **帮助 Agent 找到正确上下文、守住授权边界、保存真实验证证据，并在交付时检查结果的薄层。**

但需要区分两件事：**模型能力增强，可以减少过程干预；授权、数据安全、验证真实性和交付一致性，不能靠模型能力替代。**

下面是基于当前代码的具体判断和改造方案。

# 一、审查基线与总体判断

本次审查固定在：

* 仓库：`Ancienttwo/repo-harness`
* 提交：`2c00d4da5d0d769223791791c01ae6b501ab2c5f`
* `package.json` 版本：`0.19.2`。

阅读覆盖了主要执行链：**Hook 路由与处理器 → 工作流分级 → 状态解析 → 任务契约与验证 → Stop/恢复 → 配置和模板 → 相关测试、CI 与已有基准报告**。这是一轮静态代码审查；本轮没有运行测试或重新测量性能，因此下文会区分代码事实、历史测量与改造目标。

## 1.1 你的方向正确，但当前版本不是“还没做过简化”

代码里已经有不少正确的减负设计：

| 已有机制          | 当前实现                                 | 我的判断        |
| ------------- | ------------------------------------ | ----------- |
| 三档工作流         | `lite / standard / strict`           | 保留，不再增加第四档  |
| 普通任务不要求独立契约   | Standard 的 `separate_contract` 默认不要求 | 应让实际使用路径遵守它 |
| 单次 Hook 内复用状态 | `StateInputCollector` 惰性、一次性解析       | 保留          |
| 编辑后延迟处理       | PostEdit 最多写一个小型 journal event       | 保留，不退回逐次同步  |
| 验证证据复用        | 审查、结束和交付消费已有证据                       | 保留并收敛入口     |
| 限制额外审查        | 每工作包一次语义审查、默认零次跨模型咨询                 | 保留          |
| 提示词显式路由       | 普通文本绕过历史分类器                          | 不需要再做一遍     |

这些不是新方案，而是已经落地的基础。真正的问题是：**外围策略、模板、状态依赖和结束阶段副作用，仍然让“轻量任务”承担超出其需要的成本。**

## 1.2 仓库自己的历史基准也支持重新审视流程成本

已提交的 `evals/harness/reports/profile-comparison.md` 记录了下面这组结果：

| 模式             | 场景通过数 | 报告中的 Known tokens |     平均耗时 |
| -------------- | ----: | ----------------: | -------: |
| no-harness     |   9/9 |           535,060 | 32.299 秒 |
| adaptive-lite  |   9/9 |         1,775,916 | 63.518 秒 |
| strict-harness |   9/9 |         2,502,266 | 80.530 秒 |

但这份报告生成于 **2026 年 7 月 21 日 UTC**，测试源提交是 `b32b3282…`，不是本次审查的版本。它能说明“这组场景下流程开销值得关注”，**不能证明当前 harness 无效，也不能证明三者在复杂任务上质量相同**。此外，JSON 中有缓存输入 token 等细分字段，不能把表中的 token 总量直接换算成费用。

外部工程经验也支持这种方向。Anthropic 在 2026 年 3 月的公开实验中，随着模型能力提升移除了 sprint 式实现分段，把评估从每个 sprint 改为完成后的评估；但他们也记录了“一次性大砍”导致无法复现原有效果，后来改为逐项移除、检查影响。**值得借鉴的是这种减法方法，而不是直接把某个模型名称等同于免检资格。**([Anthropic][1])

# 二、我建议的目标体验：任务可以粗，边界必须清楚

未来普通开发流程应该接近：

```text
理解目标与相关代码
        ↓
确定结果、范围和必要验证
        ↓
Agent 连续实现，自行安排内部步骤
        ↓
运行最小充分验证
        ↓
必要时进行一次独立审查
        ↓
交付或留下可恢复状态
```

**内部步骤不必全部变成仓库工件，不必每一步都派一个 Agent，也不必每一个实现动作都经过流程状态迁移。**

继续使用现有三档，但重新明确它们的使用边界：

| 任务类型                     | 应有体验                         | 不应强制要求                                 |
| ------------------------ | ---------------------------- | -------------------------------------- |
| **Lite：普通、可逆、边界明确的修改**   | 直接实现；相关检查；简洁结果和自动恢复记录        | 新建计划、契约、notes、review；失败测试日志；额外审查 Agent |
| **Standard：有一定跨度的功能或重构** | 一份明确结果与验收的工作包；连续实现；统一验证      | 按文件拆契约；为每个内部步骤建任务文档；默认外部验收             |
| **Strict：真实高风险边界**       | 明确授权范围；必要隔离；真实验证；独立验收；绑定交付版本 | 因“严格”而机械拆成大量小步骤，或强制所有缺陷采用同一种 TDD 证明形式  |

其中 Lite 和 Standard 的不少要求已经存在于策略矩阵。改造重点是**修正触发条件和消费路径，而不是重新创造同样的分级体系**。

# 三、优先改造一：停止用文件名关键词决定流程重量

这是我认为最应该优先处理的问题之一。

## 3.1 当前问题在哪里

`src/core/workflow/profile.ts` 的 `resolveWorkflowProfile()` 目前使用路径和 capability 名称中的 token 判断严格风险，例如：

```text
session             → auth
api / openapi       → public-api
schema              → schema
deploy              → deploy
release             → release
```

此外，跨 capability、`feature`、四个及以上目标路径等条件会把工作提升到 Standard。

这会把几个不同问题混在一起：

**第一，文件名字不等于真实安全边界。**
例如 `session-context.ts` 中的 `session` 可能是会话上下文拼装，不是身份认证；`src/api/` 中的内部辅助修改也不一定改变公开 API 契约。

**第二，修改跨度不等于危险程度。**
一次机械重命名可以涉及很多文件，而一行权限判断可能极其敏感。

**第三，文档路径仍可能抬高整体分级。**
状态解析虽然排除了工作流文件对路径数量的影响，但又通过 `strictScanPaths` 把原始路径集合传回严格关键词扫描。代码注释明确举了 `docs/auth/runbook.md` 的例子。需要准确区分：这类文件本身有编辑门禁豁免，但仍可能影响整体分级和后续要求。

## 3.2 建议改成什么

**风险决定“需要什么证据和授权”；复杂度决定“是否值得写计划”。两者不要再绑定成同一个粗粒度判断。**

不需要新增一套庞大的风险引擎。沿用现有 `profile.ts`、artifact matrix 和 `change-assessment.ts`，调整它们的输入含义：

| 信号                     | 建议用途              |
| ---------------------- | ----------------- |
| 已声明的鉴权、支付、数据持久化等受保护模块  | 确定性风险下限           |
| 实际部署、发布、破坏性命令          | 操作级硬边界            |
| 公开接口或持久化协议的实际变化        | 提高验证与审查要求         |
| 文件数量、跨模块数量             | 规划建议，不直接代表安全风险    |
| `session`、`api` 等名称关键词 | 提醒检查，不单独触发 Strict |
| 模型自评“风险低”              | 辅助说明，不能降低确定性授权边界  |

例如：

> 修改上下文摘要格式，可以是 Lite；修改登录会话校验，即使只有一行，也应进入 Strict。

也不能简单把全部 Markdown 排除：**可执行模板、Agent 指令、权限配置中的 Markdown，可能本身就是行为控制面。**

### 对应修改点

主要涉及：

```text
src/core/workflow/profile.ts
src/effects/state/resolve-effective-state.ts
src/core/review/change-assessment.ts
相关 profile / state / review 测试
```

建议复用已有 capability 所有权信息，只为确实敏感的模块声明稳定边界，**不要再要求每个函数、每个文件维护一份风险元数据**。现有 Change Assessment 已有 `authority_change`、`irreversible_effect`、`oracle_gap` 等原因类型，可以继续作为交付阶段的统一判断入口。

# 四、优先改造二：取消强制 TDD 顺序，保留缺陷证明与回归保护

这里必须把当前实现说准确。

## 4.1 编辑时的 TDD Guard 并不是硬门禁

`mutation-guard.ts` 会检查相关测试文件是否存在；找不到时输出：

```text
Reminder: write a failing test first, then implement.
```

UI 文件则提示先定义 Given-When-Then 场景。

**这一段只是提醒，没有阻止编辑。**因此，删除它主要减少重复提示和测试文件猜测，并不能单独解决整个流程的阻塞问题。

建议直接删除这种逐文件提醒和相邻测试文件存在性推断。

原因很简单：**测试文件是否同名、是否相邻，无法可靠说明行为有没有被覆盖。**

## 4.2 真正的硬要求在 bugfix 契约

当前 bugfix 契约要求四项：

```text
root_cause
repro
regression_guard
pre_fix_failure_artifact
```

其中回归测试还必须作为 `package_test` 出现在 Verification Plan；失败工件必须包含非零 `PRE_FIX_EXIT=` 和对应测试路径。这些要求同时出现在模板、文档与验证实现中。

这对容易复现的纯逻辑缺陷有价值，但作为所有 bugfix 的统一门槛过窄。

还有一点值得注意：

> **“某次测试非零退出，日志里有测试路径”本身，并不能证明它确实因为目标缺陷而失败。**

因此，流程可能付出了保存和解析失败工件的成本，却仍然需要人工或模型判断失败原因是否相关。

## 4.3 建议采用的测试政策

我的建议是：

> **不强制测试必须先于实现；要求最终验证能说明改动解决了什么问题、覆盖了什么边界，以及还有什么没有验证。**

| 修改类型          | 建议验证方式                               |
| ------------- | ------------------------------------ |
| 易复现的逻辑 bug    | 优先补回归测试；证明它能区分错误行为与正确行为              |
| 已有失败测试覆盖的 bug | 复用原测试，不为流程再造一个失败工件                   |
| 平台、进程、安装、集成问题 | 接受真实入口复现、日志、smoke 或前后运行读回            |
| 不改变行为的重构      | 使用既有行为测试和必要集成检查，不制造“先失败”             |
| 普通文档、文字、样式调整  | 做对应文档或实际界面检查，不要求新增产品单测               |
| 权限、支付、数据完整性问题 | 要求强验证与适当独立审查，但不限定为一种 `bun test` 日志形式 |

对值得验证的回归测试，可以在实现后用隔离的旧版本验证它能否复现问题，**不必为了形式上的时间顺序，要求 Agent 必须先产生红灯再碰实现**。

没有条件复现时，也不能伪造证据。应明确记录：

> 已验证当前行为；未在原始环境复现；剩余风险是什么。

高风险且缺少必要验证的任务仍然不能交付。

## 4.4 不要另建一套“更灵活但更复杂”的测试证据框架

仓库现有 Testing Policy 已经要求：

* 优先使用最小充分覆盖。
* 不为新增文件自动新增测试文档。
* 不因缓存未命中或提交变化自动重跑全套。
* 由一个执行者准备证据，审查者消费证据。
* 区分当前验证和历史 baseline。

这些方向已经很好。此次应当**删除与它们冲突的强制形式要求，而不是重新写一套同样长的新政策**。

落地上，保留现有执行记录与 Verification Plan。将 bugfix 证据要求改为能引用既有测试、运行读回或明确未验证状态；不要让普通任务为了填写这些内容再生成多份 JSON 和 Markdown。

# 五、优先改造三：把任务边界从“文件清单”提升到“完整工程结果”

这一点有非常直接的代码证据。

## 5.1 过细边界已经影响代码质量

在 `src/cli/hook/mutation-observed.ts` 中，`normalizeFilePath()` 的注释明确说明：

> 之所以重新移植而不是导入已有实现，是因为 `mutation-guard.ts` 不在当时任务的 Allowed Paths 中。

同一段注释还提到 `session-context.ts` 中有类似情况。

这说明问题不只是“任务文件太多”。

**当任务范围细到阻止必要的公共函数复用时，harness 已经在推动 Agent 选择局部合规、整体更差的实现。**

## 5.2 新的拆包原则

我建议以后按以下边界拆工作包：

> **可以独立验收的工程结果，而不是可以独立编辑的文件集合。**

例如，不建议这样拆：

```text
任务 A：新增一个状态 getter
任务 B：给 getter 加调用
任务 C：修改对应 hook
任务 D：补一个公共 helper
任务 E：再处理三个调用方
```

更适合这样：

```text
工作包：普通编辑只读取授权相关状态

结果：
- 普通编辑不再构建完整 review / handoff 状态。
- 所有相关入口使用同一授权事实来源。
- 路径、工作树和高风险边界检查不退化。
- 对应行为测试与入口测试通过。
```

Agent 可以在这个结果范围内，自行决定函数提取、调用顺序和测试组织。

## 5.3 `allowed_paths` 应保留，但调整用途

建议把它定位为：

**保护无关工作和限制受托范围，而不是预先规定实现必须经过哪些文件。**

具体做法：

* 普通单 Agent 工作不为每个内部步骤新建范围契约。
* 工作包范围应涵盖同一行为链的实现、公共 helper、调用方及测试。
* 多 Agent 并行时，才需要更明确的写入所有权和冲突边界。
* 新增产品功能、改变权限边界、影响其他工作包，仍需显式扩展范围。
* 不允许执行 Agent 因为觉得限制烦，就自行忽略旧契约。

对陈旧 active contract，应该修复**任务关闭与 active marker 解绑**的生命周期，而不是静默把不合法状态当成“没有限制”。

## 5.4 契约模板应按需生成，而不是处处填“不适用”

当前 `contract.template.md` 同时包含 Root Cause、Workflow Inventory、Change Assessment、Acceptance Policy、Allowed Paths、Evidence Requirements、Delegation Contract、Verification Plan、Acceptance Notes 等区块，即使某些区块对该任务完全不适用。

建议：

**Lite：**不新增手写任务工件。

**Standard：**一份工作包足够，包含目标、范围、验收、重要风险。

**Strict：**保留执行契约，但只生成适用内容。没有委派就不生成完整 Delegation Contract；没有 benchmark 消费就不写 benchmark 区块；没有独立决策就不生成 notes。

机器能确定的默认执行字段，由工具展开到现有 Verification Plan。**展开后的计划是唯一执行权威，不保留两份可独立编辑、需要双向同步的命令列表。**

# 六、优先改造四：缩小状态解析，而不是继续优化一个越来越大的解析过程

这是最明确的运行时优化方向。

## 6.1 当前“只解析一次”不等于内部只收集一次

`StateInputCollector` 已经做到每个事件只调用一次相应 resolver，这值得保留。

但 `resolve-effective-state.ts` 的内部过程仍然很重：

```text
读取 policy / active markers
读取 plan / contract
构建 Git review subject
解析 capability / Archcontext 节点
读取 review / checks / repair
读取 sprint / handoff / resume / current
计算各类 revision
投影完整 EffectiveState
```

稳定性检查会重复调用完整的 `resolveEffectiveStateUnlocked()`；版本提交前的确认回读，也会再次调用完整解析，然后比较授权来源的哈希。即使使用只读入口，仍然需要进行完整的稳定性解析。

**问题不是不该检查一致性，而是为了确认授权来源没变，重复构建了许多与当前动作无关的信息。**

## 6.2 建议拆成“按用途读取”，不是新增第二权威

保留现有文件和解析规则，将消费方式区分为：

| 消费场景              | 应读取的主要信息                      |
| ----------------- | ----------------------------- |
| 编辑前               | 当前授权、路径归属、工作树所有权、必要的风险边界      |
| SessionStart / 恢复 | 当前任务摘要、未完成事项、证据引用             |
| 交付前               | 完整 Git subject、检查证据、审查、目标分支状态 |

这些是**同一权威数据的不同读取视图**，不是新建三套状态机。

具体建议：

**第一，稳定性确认只重读相关授权指纹。**
不再为了比较授权来源，重算 review、handoff 等完整视图。

**第二，普通编辑不发布无关的状态投影。**
是否需要写全局版本或完整缓存，应由真正消费该版本的操作决定，而不是每次状态查询顺带发生。

**第三，保留一次事件内的惰性复用。**
不引入常驻守护进程，也不需要为此上数据库。

**第四，最终交付重新核对完整 subject。**
热路径变轻，不意味着交付检查信任旧结果。

缓存不能只绑定 `HEAD`。工作区修改、策略、active contract、capability 授权来源和路径解析结果都可能变化。**不要用 TTL 取代授权一致性检查。**

## 6.3 测量也要调整，否则可能优化错方向

当前 `event-telemetry.ts` 明确说明：

> `child_processes` 只统计路由运行时直接启动的子进程，不包括 handler 内部 Git/Bun 调用。

因此，“`child_processes = 0`”是一个有明确口径的架构哨兵，**不是总进程成本为零**。对应 characterization 测试也在固定这个口径。

建议保留旧指标语义，另外在性能采样中统计：

```text
端到端 Hook 耗时
完整状态构建次数
内部 Git / Bun 调用次数
实际文件读取与写入
冷启动成本
```

不需要建设一个新遥测平台；先把现有基准的测量范围补准确。

# 七、优先改造五：把 Stop 变回“保存并退出”，不再承担维护任务

## 7.1 当前 Stop 的职责太多

`runStopHandler()` 在 Lite 的提前返回之前，已经可能处理：

```text
Git 架构变更集合
架构投影队列
旧架构 cascade
projection restamp publication
PostEdit journal
checkpoint
handoff / resume / event / run-summary
清理旧记录
完整状态解析
minimal-change enforce
重构建议
```

其中架构投影有独立的严格失败门禁；minimal-change 的 enforce 也特意放在 Lite 返回之前。另一方面，`readyToShip=false` 只给提示、不阻止 Stop，这部分区分已经做对了。

不能把上述内容全部理解为“每次都会执行昂贵工作”，因为有条件判断和开关。但**这些职责仍然耦合在普通结束路径上**。

## 7.2 有一个特别值得移出的副作用

`restamp-publication.ts` 能在符合条件时执行：

```text
git add <manifest>
    ↓
git write-tree
    ↓
git commit-tree
    ↓
单路径差异证明
    ↓
git update-ref CAS
```

这是**本地机器提交**，不是远端推送；代码有单路径证明、WIP 防护和 CAS，不应说成随意提交用户代码。但它确实会在 Stop 路径上改变当前分支的提交状态。

我的建议很明确：

> **把这种提交行为移到显式架构维护或交付准备命令，不放在通用 Stop 内。**

保留它已有的安全检查，只改变触发边界。

## 7.3 新 Stop 的职责边界

建议只保留：

```text
提交必要恢复记录
保存已有验证证据的引用
说明还有哪些工作未完成
退出
```

需要精确恢复的活动任务，其必要持久化失败仍应明确报错；但普通任务不应因为可选架构投影、风格建议、额外重构建议而被迫继续。

相应变化：

**架构投影：**普通编辑只记录需要更新的事实；在显式同步或确实要求架构证据的交付点执行。

**Minimal change：**从结束阻塞改为工作包级的一次性建议或审查输入。新增依赖可以是审查信号，但不应该仅凭“出现了新依赖”就让已完成普通任务进入新循环。

**重构建议：**默认留作建议，不自动转化为当前任务必须完成的新工作。

**恢复工件：**复用既有权威记录，按实际变化更新；没有活动任务、没有新进度时，避免为了退出而不断重写恢复文档。

还有一个迁移细节：当前架构执行偏好的权威在用户级 `~/.repo-harness/config.json#architecture`，不是随意新增一个仓库开关就能覆盖。修改默认体验时，应同步处理安装、升级和用户已显式选择的行为。

# 八、优先改造六：收敛上下文、解析器和可选能力

## 8.1 根上下文应该只描述全仓规则，不携带某个模块的当前状态

当前根 `AGENTS.md` 的生成式 Architecture Contract 指向：

```text
Functional block: src/effects/automation
Capability ID: runtime-harness-automation-budget
Last changed path:
src/effects/automation/campaign-capability-registry.ts
```

这类模块特定上下文出现在根规范中，会让根文档混入一个局部模块视角。

建议：

**根文档只保留稳定的全仓信息：**产品目的、真实安全边界、代码导航、验证入口和禁止事项。

**模块上下文留在模块附近：**责任、关键入口、相关测试、依赖边界。

**当前工作状态只在恢复入口提供：**不再写进长期规范。

当前已有 SessionStart 约 1,500 estimated tokens 的预算与去重机制，但它并不等于整个 Agent 上下文预算；根规范和局部规范的注入需要一起评估。

另外，`docs/spec.md` 仍写着 “Hooks remain fail-open observers”，但代码中的 PreEdit 和部分 Stop 路径会阻塞。这应被修正为清晰的分类：

> 安全与授权检查可以阻塞；观察与建议不阻塞；交付检查只决定能否交付。

不要让模型同时收到互相矛盾的原则。

## 8.2 收敛 Shell 与 TypeScript 的重复契约解析

`verify-contract.sh` 不只是一个薄启动器：它包含 YAML 注释处理、字段解析、Root Cause 字段与占位符判断。相关逻辑又与 `contract-run.ts` 配对维护，注释说明部分一致性依赖共同 fixtures，而不是共享解析函数。

建议把**契约解析、规范化和元数据验证收敛到一个类型化实现**，Shell 保留兼容入口和必要进程编排。

不要借机引入通用 DSL。目标是：

```text
一份契约
一个解析结果
一个验证判断
多个薄入口
```

这样以后修改 bugfix 证据要求，不需要同时维护 Shell、TypeScript、模板、角色提示词中的多个独立判断。

## 8.3 普通 harness 不应默认承担完整 Agent 工厂的安装与加载责任

当前 policy 中的 agent fleet 包含七种角色，并配置了 `auto-install-on-init`；包发布流程又同时构建 Hook bundle 和 operator web UI。`handler-registry.ts` 也在模块顶部导入各类处理器及架构队列依赖。

建议先做**调用和安装边界隔离**，不要立即拆成很多 npm 包：

| 能力                              | 建议默认        |
| ------------------------------- | ----------- |
| 基础上下文、边界检查、证据、恢复                | 核心          |
| 常规单 Agent 开发                    | 直接使用宿主能力    |
| 专用 fleet、Module Engineer、无人值守编排 | 明确启用后安装和初始化 |
| 架构投影与高级 UI                      | 按需加载和执行     |

未启用的能力应尽量做到：

> 不初始化、不扫描状态、不注入提示、不要求工具就绪。

路由级加载优化需要看真实构建产物和冷启动测量，不能因为代码里写了动态导入就宣布性能改善。

同时，现有 Hook 的 event、route ID、matcher 和顺序涉及宿主适配与信任行为。**不能为了减少几个入口就直接重排或删除路由；必要变化应伴随适配器迁移和契约测试。**

# 九、测试与验证本身如何减负

我不建议按“测试文件数量减半”设目标。

更好的目标是：

> **删除没有独立失败检测价值的重复覆盖，减少昂贵 fixture 重建，避免同一证据被重复生产。**

## 9.1 先收敛本地必跑检查

根规范列出的本地检查覆盖 Hook、helper、reference-config 投影，部署 SQL、架构同步、任务同步、任务工作流、仓库检查和 init dry-run。即使产品测试已经选择得很精简，这些治理检查也可能成为另一笔固定成本。

建议建立一个**简单、显式的检查归属表**，复用现有命令：

| 改动面          | 本地主要检查              |
| ------------ | ------------------- |
| 普通源码行为       | 对应行为测试与必要类型检查       |
| Hook 实现或宿主输出 | 对应入口测试、Hook 投影检查    |
| helper 源或模板  | 对应 helper/模板检查      |
| 工作流策略与任务状态   | state/workflow 相关检查 |
| 包发布或安装路径     | 对应真实产物和安装 smoke     |
| 普通非执行文档      | 相关文档完整性检查           |

不需要再建一个聪明但难以验证的自动测试选择引擎。未知影响先追踪；仍无法界定时，明确升级相关检查，不能默认为“没有测试需要运行”。

**现有 CI 和 release 门禁先保留。**仓库已经区分 governance / functional 两条 CI lane，测试脚本也有实际的隔离文件并行池，不应再把“增加并行”作为未经测量的新方案。

## 9.2 测试合并必须对应同一个失败模式

例如 `tests/state-input-collector.test.ts` 中，有多个案例验证同一 resolver 在多次读取下只调用一次。这是可以检查是否合并的候选，但该文件中“合法 null 被缓存”“不同事件重新解析”“构造阶段零读取”等案例检测的是不同问题，应保留。

比较值得清理的测试是：

* 只固定历史提示文案，而文案并非公共协议。
* 通过扫描源码文本判断功能存在。
* 为不同纯输入分支重复完整安装。
* 多个文件重复覆盖同一包装层，却没有检测不同边界。

但真实权限、恢复、进程清理、跨平台和发布产物测试，不应因表面输入相似就删除。

# 十、建议拆成四个实质性 PR，而不是几十个微任务

每个 PR 都应完成一个能验收的结果。不要把“简化 harness”本身再做成一场过细的 harness campaign。

| PR                    | 核心结果                     | 主要改动                                             | 验收重点                                  |
| --------------------- | ------------------------ | ------------------------------------------------ | ------------------------------------- |
| **PR 1：普通任务不再误进入重流程** | 分离复杂度与风险，修正文档与默认体验       | `profile.ts`、状态风险输入、根上下文、对应策略测试                  | `session/api` 名称不再单独触发严格档；真实受保护边界仍被识别 |
| **PR 2：任务与测试证据去形式化**  | 不强制 TDD 顺序；契约按需生成；解析判断收敛 | contract 模板、Root Cause 验证、Shell/TS 共享解析、委派 brief | 真实回归与运行证据可使用；缺失证据不伪装通过；普通任务不产生无用工件    |
| **PR 3：Hook 热路径变薄**   | 编辑只读必要授权，Stop 不做额外维护     | state resolver、mutation guard、Stop、架构发布触发点       | 一致性与授权不退化；普通 Stop 不生成架构提交；必要恢复可用      |
| **PR 4：可选能力与验证成本收口**  | 未启用能力不干扰普通开发，清理重复检查      | handler 加载、安装选择、本地检查归属、测试 fixture                | 最小安装可用；宿主协议不破坏；实测运行与维护成本下降            |

有两个实施约束很重要。

**第一，修改安全策略的 PR，必须按修改前的目标分支策略接受审查。**不能让候选代码先放松自己的验收条件，再声称自己合规。现有 merge gate 读取精确目标 base 的策略并绑定 receipt/seal，这个设计应保留。

**第二，不原地改写历史验收证据。**新任务使用新规则；运行中的契约通过明确升级或关闭流程迁移；历史记录保留原有身份和验证语义，不能重新包装成新规则下的“通过”。

# 十一、怎么证明简化有效，而不是只是把门禁删掉

## 11.1 先用行为标准验收

我建议把以下结果作为必须验证的目标，而不是先承诺某个性能百分比：

| 场景              | 简化后的预期                                  |
| --------------- | --------------------------------------- |
| 普通小修复           | 不强制创建 plan/contract/notes/review        |
| 非同名测试已覆盖目标行为    | 不再因“找不到相邻测试文件”提示 TDD                    |
| bugfix 使用真实运行证据 | 不再被唯一 `package_test + pre-fix log` 形式排除 |
| 普通多文件机械修改       | 不因文件数量被误判为高风险                           |
| 真实权限或数据边界修改     | 必需验证和授权仍然存在                             |
| 可选架构工具失败        | 普通任务可以保存状态并停止，不伪称已完成架构维护                |
| 普通 Stop         | 不运行新的维护性提交流程                            |
| 相同输入、已有有效验证     | 不因换了审查角色而重新执行                           |
| 验证失败、证据陈旧、目标冲突  | 不允许错误地交付                                |

此外，必须保留针对路径逃逸、工作树归属、目标分支变化、陈旧 receipt 和进程清理的负向测试。

这里还应坚持仓库已有的边界认识：**本地 Bash 不是文件系统沙箱，Edit/Write Hook 也不能证明覆盖所有 shell 写入。**最终 Git 差异检查和宿主权限/隔离必须各自承担真实职责，不能把一个路径清单包装成不存在的安全保证。

## 11.2 复用现有基准，不再发明一个庞大的评测工程

建议普通 PR 只运行确定性的相关检查。

在主要改造集成后，再使用已有场景做一次：

```text
当前版本
    vs
简化候选版本
```

固定模型、宿主版本、工具权限、仓库快照与输入。`no-harness` 可以作为发布前的参照，不必每个 PR 都重新跑所有档位、所有模型。

重点观察：

**结果质量：**功能验收、真实回归、越界修改、未完成却报告完成。

**用户体验：**首次有效编辑时间、总完成时间、阻塞次数、需要人工解除的流程次数。

**系统成本：**缓存与非缓存 token 分开，Hook 耗时、内部进程调用、完整状态重建、新增任务工件分开。

少量样本只报告观察结果，不把全部 9/9 当成质量等价证明。对关键差异场景补少量重复运行即可，避免评测消耗反过来超过简化收益。

# 最终建议

**我建议你推进这轮简化，而且可以比“少写一点提示词、少跑几个测试”更彻底。**

最先动的应当是：

**风险误升级、强制 pre-fix 工件、过细 Allowed Paths、完整状态反复构建，以及 Stop 中的非必要工作。**

最应该保留的是：

**统一权威、真实验证证据、明确授权、必要隔离、可靠恢复和交付时的版本一致性。**

最终的产品定位可以收敛成一句话：

> **repo-harness 不负责规定强模型如何完成每一步；它负责让模型知道目标和边界，并让用户能可靠判断工作是否完成。**

任务内部怎样拆分、什么时候写测试、是否提取公共函数、是否需要子 Agent，尽量交给模型；**是否越权、是否真的验证、证据对应哪个版本、能不能交付，继续由明确且尽量少的机制决定。**
