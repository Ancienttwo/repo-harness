# repo-harness 0.15.0 release preparation

## Goal

Prepare `repo-harness@0.15.0` from `v0.14.2..main` as a frozen, verifiable release candidate, merge it to `main`, and push the exact candidate commit. Stop before npm publication, tag creation, and GitHub Release creation.

The minor bump is required because the range contains `feat(hook): add repo-level architecture drift changed-set authority`; the remaining behavior changes and fixes are backward-compatible within that new capability.

## Success Criteria

- Every repo-owned release version authority and public current-release projection says `0.15.0`.
- `docs/CHANGELOG.md` contains an accurate `0.15.0` entry for `v0.14.2..candidate`.
- A dated release filing records scope, candidate evidence, pending public actions, and rollback.
- Version consistency, targeted release/version tests, repository required checks, package contents, and tarball install smoke pass on the frozen candidate.
- The workflow contract, receipt, review, and archive sequence closes cleanly; the candidate is merged and pushed to `main`.
- npm remains unpublished and `v0.15.0` remains absent until a later explicit release authorization.

## Scope

- Bump `package.json`, `assets/skill-version.json`, the five README current-release projections, and `scripts/axr7-consumer-e2e.ts` to `0.15.0`.
- Add `docs/CHANGELOG.md` release notes for the changed-set authority, Stop diff cutover, retired journal architecture bit, and cascade-ack cursor fix.
- Add `deploy/release-checklists/260812-repo-harness-0.15.0.md` with exact source range, evidence, pending-publication state, release sequence, and rollback.
- Update only generated architecture/task projections required by the workflow tools for this release slice.

## Non-scope

- No feature, compatibility shim, dependency upgrade, or refactor beyond release metadata and required deterministic projections.
- Do not change the unrelated fake Oracle version string in `tests/cli/chatgpt-browser.test.ts`.
- Do not rewrite historical release filings, archived workflow artifacts, active unrelated plans/contracts, or the legacy `.claude/.skill-version` repository stamp unless a current consistency check proves it is an authority.
- Do not run `npm publish`, create/push `v0.15.0`, create a GitHub Release, or mutate the selected Bun-global installation.

## Constraints

- One source of truth: `package.json.version` must equal both fields in `assets/skill-version.json`; README and AXR7 values are deterministic release projections verified against it.
- The candidate commit must be frozen before expensive release evidence is produced. Existing evidence may be reused only when subject and freshness checks pass.
- Public publish actions require a later explicit authorization and successful post-merge CI.
- After npm publication, correction is forward-only; the version and tag must never be reused or moved.

## P1: Architecture Map

- Release version authority: `package.json.version` plus the enforced workflow stamp in `assets/skill-version.json`.
- Human projections: five READMEs and `docs/CHANGELOG.md`.
- Consumer/package proof: `scripts/axr7-consumer-e2e.ts`, `scripts/check-skill-version.ts`, npm `prepack`, `scripts/check-npm-release.sh`, and `scripts/check-tarball-install-smoke.sh`.
- Operations surface: `deploy/release-checklists/` owns the durable filing; npm registry, git tag, GitHub Release, and Bun-global install are later external mutation boundaries.
- Workflow authority: plan, contract, review, receipt, task status, and architecture projections generated by repo-harness.

## P2: Concrete Trace

`package.json.version` enters npm packing and the bundled hook build; `assets/skill-version.json` supplies downstream workflow/template stamps. The consistency check rejects divergence. `npm pack` runs `prepack`, builds `dist/hook-entry.js`, and produces the exact tarball consumed by the clean-install smoke and AXR7 fixture. After a later publish, registry, tag, GitHub Release, and exact global install readbacks would prove the public state. This slice ends after the candidate is merged/pushed and post-merge CI is known.

## P3: Decision Rationale

Use a single backward-compatible minor release, `0.15.0`, because the range adds a public hook capability and changes its internal authority without a breaking interface. Keep release preparation separate from irreversible publication so a bad candidate can still be reverted. At 10x dirty-tree size, Stop fan-out remains the first known pressure point; it is already deferred with a measured trigger and does not justify broadening this release slice.

Rejected alternative: `0.14.3` is too small under the repository's release rule because `v0.14.2..main` contains a `feat` commit. Rejected alternative: combining publish/tag/Release into preparation would cross the rollback boundary before the user reviews the candidate.

## Public Interfaces

- npm package version becomes `0.15.0`.
- Generated workflow stamp becomes `repo-harness@0.15.0+template@0.15.0`.
- No CLI flags, config schema, environment variables, or external dependencies are added.
