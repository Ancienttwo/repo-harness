## Problem

Worker lifecycle is asynchronous effect orchestration. It needs durable runtime receipts and exact idempotency independent of semantic verification. Persistent main Sessions and temporary Workers remain separate adapter families.

### Product Direction

Persistent main Sessions and temporary Workers are separate effect families. `CodexPersistentThreadTransport` maps create/resume/read/send/observe/archive to Codex App Server operations and events, but a Thread remains only the current Engineer Binding's runtime carrier. `send` accepts only an already-persisted ME-1C message event digest/attempt and returns a delivery observation；it cannot accept arbitrary task instructions or create workflow state. Unknown effect outcomes enter reconciliation rather than blind retry.

The Host dispatches a content-addressed context resource by explicit MCP resource/CLI read, never by injecting the full packet at SessionStart. SessionStart retains the global 1,500-token budget; packet bytes are capped at 32 KiB and fetched only for an admitted run. The same summary-and-reference rule applies to persistent Thread delivery.

### Feasibility Boundary

- **Confirmed**: local processes, MCP resources and immutable receipts are feasible.
- **[UNKNOWN]**: uniform suspend/revoke controls across Codex/Claude Provider Sessions.
- **Fail closed**: unknown dispatch outcome enters reconciliation, not blind retry.

## Acceptance Scenarios

### Scenario 1: Lost acknowledgement

Dispatch succeeds but acknowledgement is lost. Same idempotency key returns/collects the original run; it does not spawn a second Worker.

### Scenario 2: Host restart

Host restarts with an active read-only run. It reconstructs runtime state from receipts/provider observation or marks reconciliation required.

### Scenario 3: On-demand packet

SessionStart receives only compact refs. Worker fetches the exact packet digest through the declared MCP resource/CLI channel after admission.

### Scenario 4: Persistent Thread lost acknowledgement

A persisted ModuleMessage event is sent to a current Codex Binding and the App Server turn starts, but the transport acknowledgement is lost. Reconciliation observes the exact Thread/turn relation and appends one delivery observation; it does not submit a second turn. Binding rotation makes an assignment-scoped request stale before any further effect.

## Non-goals

- Semantic verification, writable grant policy, task election or Acceptance.
- Full transcript persistence or automatic Provider fallback.
- Remote/cloud Host in P0.
- Task/Lease/Work Package assignment, message persistence, semantic completion or Kanban column ownership inside the Provider adapter.

## Module Behaviors (P0)

### Module 1: Adapter Boundary

`PersistentThreadTransport` owns long-lived Session create/resume/read/send/observe/archive. The Codex adapter speaks App Server JSON-RPC/events; other Provider adapters must expose the same closed capability/result taxonomy. Lifecycle operations are fenced to operator/Host authorization and current Binding where applicable. Message send is legal only after ME-1C persistence and emits `ModuleMessageDeliveryObservationV1`. `WorkerRuntimeAdapter` owns temporary run lifecycle. Their identities, idempotency keys and retries never alias.

Activation is staged without changing authority: ME-3A enables only `PersistentThreadTransport` after ME-1C；ME-3B enables `WorkerRuntimeAdapter` only after ME-2A admission and ME-2C context contracts are Approved. Neither stage enables ME-2B writer grants.

### Module 2: Runtime Receipts

Persist immutable dispatch intent/idempotency before effects; publish observation receipts and one current pointer under exact run identity. Provider success with missing receipt publication enters reconciliation and never authorizes a second dispatch.

## Data Model

```yaml
WorkerDispatchIntentV1:
  protocol: 1
  kind: repo-harness-worker-dispatch-intent
  dispatch_id: sha256(adapter_kind + idempotency_key)
  idempotency_key: bounded-opaque
  operation_fingerprint: sha256(canonical dispatch request)
  delegation_id: uuid
  admission_receipt_sha256: sha256
  round_index: integer
  adapter_kind: closed-enum
  context_packet_sha256: sha256
  requested_at: datetime
  intent_sha256: sha256

WorkerRuntimeReceiptV1:
  protocol: 1
  worker_run_id: uuid
  dispatch_intent_sha256: sha256
  delegation_id: uuid
  round_index: integer
  adapter_kind: closed-enum
  runtime_principal_id: opaque|null
  context_packet_sha256: sha256
  state: admitted|dispatching|running|collecting|completed|cancelled|failed|reconciliation_required
  observation_revision: integer
  previous_receipt_sha256: sha256|null
  failure_class: none|admission|infrastructure|provider|cancelled|unknown
  provider_run_ref: opaque|null
  receipt_sha256: sha256

WorkerRuntimeCurrentV1:
  protocol: 1
  dispatch_id: sha256
  dispatch_intent_sha256: sha256
  worker_run_id: uuid|null
  current_receipt_sha256: sha256|null
  state: dispatching|running|collecting|completed|cancelled|failed|reconciliation_required
  current_digest: sha256
```

Packet channel is exactly one content-addressed MCP resource with an equivalent explicit CLI read for local operators. Neither path auto-loads the packet into SessionStart.

Dispatch is create-intent-first. The same key with the same fingerprint resumes/collects the original dispatch; the same key with different request bytes fails `idempotency_conflict`. After intent fsync the Host may call the Provider once. If Provider effect succeeds but run/current publication fails, the current state is `reconciliation_required`; only a positive adapter observation bound to the exact intent may publish the recovered `worker_run_id`. Absence or unknown observation never triggers a second Provider effect. Receipt transitions use `previous_receipt_sha256` CAS and publish `WorkerRuntimeCurrentV1` only after the immutable receipt is durable.

## Known Unknowns

| Item | Impact | Resolution Path | Owner |
|---|---|---|---|
| Provider lifecycle parity | Adapter scope | per-provider capability matrix | Runtime owner |
| Managed Parent revoke/suspend | Blocks ME-2B | dedicated security canary | Host owner |
| Codex App Server operation/event idempotency | Blocks automatic lifecycle/send | per-operation lost-ack matrix and exact Thread/turn reconciliation | Provider owner |

## Developer Handoff

Start with ME-3A persistent-thread delivery. Unknown outcomes reconcile；never silently retry on another adapter. ME-3B remains disabled until ME-2A/2C are Approved, and writable Parent control remains disabled until the separate ME-2B gate.

### Acceptance Scripts

1. Lose dispatch acknowledgement and prove one Worker run.
2. Restart Host and recover/mark reconciliation without duplicate effects.
3. Race cancel and collect; assert one terminal revision.
4. Measure SessionStart and packet budgets separately.
5. Verify persistent Thread and Worker adapters cannot consume each other's run refs.
6. Retry one key with changed context or admission bytes and assert `idempotency_conflict`; crash after Provider success and before receipt publication and assert reconciliation without a second dispatch.
7. Canary Codex create/resume/read/send/observe/archive; lose each acknowledgement after Provider effect and prove reconciliation never duplicates a Thread or turn, while no operation mutates Task/Lease/Acceptance bytes.
