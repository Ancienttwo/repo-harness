## Background and Goals

This proposal grows the operator console from a read-only board into a local management console. It does only three things: manage the dev environment, manage development and architecture docs, and track progress. Writing code still happens in the user's own harness. The only work the console hands to an agent is writing docs, and changes come back as a Draft PR. Agents connect through OAR. The design is on the [design canvas](https://claude.ai/code/artifact/8d9f19a4-d9a0-4d19-88bc-af5eb110d812).

- **Current state**: `src/operator-web` is about 4.1k lines of React + Kumo, with 8 pages. `operator serve` listens only on the loopback address. Any method other than GET/HEAD returns 405, so the console has no writes today. Sending a message to an owner has only a CLI entry point, `fleet message send`, which the Bot calls.
- **Reference**: the desktop app shell of the open-source project magpie. We borrow three things: a sidebar grouped by function, hairline-separated row lists with a "show the other N" (显示其余 N 个) collapse, and a marketplace-style card grid.
- **Goal 1 · Dev environment**: see the hook, skill, MCP, and profile status of each host (Claude Code, Codex) in one place. When there is drift, give a fix command for the user to run in the terminal. The CLIs installed on this machine are also listed in one place, and unused ones get an uninstall command. The connection status of each Bot through MCP, Slack, and herdr is also visible in one place.
- **Goal 2 · Docs**: read development and architecture docs under docs/ in the APP, cite passages, and hand them to an agent to edit. Changes come back as a Draft PR. Re-home each kind of doc and state into two levels: global and repo.
- **Goal 3 · Architecture**: render three kinds of architecture diagrams (layers, sequence, topology) on a canvas. Selecting an element shows its code size, dependency edges, and Remarks.
- **Goal 4 · Tests**: group the test scripts under tests/ by module, and show run commands, recent results, and TDD red/green status.
- **Goal 5 · Progress**: one person, in one window, sees which work is waiting on them, what stage each task is in, and which agent is working on it. Follow-up goes back to the user's own harness, or to the Bot.
- **Non-goals**: no writing code in the console, and no sending messages to or stopping coding sessions; no mobile version; no drag-and-drop dispatch; no recomputing column, attention, or merge readiness in the UI; no showing internal implementation names other than OAR.

## Design Principle: AI Writes, Humans Read Diagrams

The console is designed for one person or a small team. Agents write code and docs. Humans step in at only three gates, and judge mainly by reading diagrams. We skip the traditional SOP pieces: review meetings, long design docs, and hand-drawn architecture diagrams. Rules that can be checked automatically go to CI; humans look only at exceptions.

| Principle | What the console does | Basis |
| --- | --- | --- |
| Humans read intent, not every line | The board and drawer show goals, non-goals, acceptance criteria, and change impact first; the diff is collapsed by default | Anthropic merges 30,000+ changes a day; humans read the intent of a change, not every line ([Redesigning source control](https://anthropic.com/engineering/redesigning-source-control), 2026-10-13) |
| Agents verify their own work and hand over evidence | Every task needs a check that can run: tests, build, screenshot comparison; pages show evidence, not claims of "done" | [Claude Code best practices](https://code.claude.com/docs/en/best-practices): give Claude a check it can run, and have it show evidence instead of claiming success |
| Automated checks allocate human attention | Violations, failures, and high-risk changes are marked red and pinned to the top; low-risk changes are only counted | [2026 Agentic Coding Trends Report](https://claude.com/resources/guides/2026-agentic-coding-trends-report/priorities-for-the-year-ahead): use automated review to direct human attention to what matters most; the repo's Review by risk tiers |
| Diagrams first, text second | Architecture, tests, and progress all lead with a diagram: one base map plus switchable layers; text goes into hovers and drawers | The product owner's premise: humans read diagrams more directly and more accurately than text; repo UI rule: let the layout explain |
| Second opinions use fresh context | The agent that wrote the work does not review it; review uses a fresh-context subagent that reports only gaps affecting correctness | Claude Code best practices: adversarial review; the planner, generator, and evaluator roles in [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps) (2026-03-24) |
| Process scales with risk | Changes you can describe in one sentence get no plan; medium risk gets one fresh-context review; high risk adds cross-model review | Claude Code best practices: skip the plan for a diff you can describe in one sentence; Review by risk in the repo's `agentic-development-flow.md` |
| Docs are a by-product | The agent drafts architecture model updates and decision records in the same PR; humans confirm intent and do not write them by hand | Repo rule: branches that change responsibilities update the model per `repo-harness-architecture` |

There are only three human gates:

1. **Set intent**: goals, non-goals, acceptance criteria.
2. **Review exceptions**: violations, failures, and high-risk changes flagged by automated checks.
3. **Guard hard boundaries**: publishing to main, deletion, credentials and permissions, release and production (the four hard boundaries in `CLAUDE.md`).

Traditional steps we do not do: architecture review meetings, a long design doc per feature, hand-drawn architecture diagrams, line-by-line code review, production-readiness reviews for local tools.

## Write and Permission Boundaries

The console has no writes today: the server returns 405 for any method other than GET/HEAD. This proposal adds only three bounded writes. The constraints to revise are in the constraint table at the end of this section. Each write has a fixed target, a fixed scope, and a visible failure state.

| Write | Target | Scope | Not allowed |
| --- | --- | --- | --- |
| Enable / disable an agent, set uses and the default docs agent | `~/.repo-harness/config.json` | Local config | Storing credentials; editing the host's `~/.claude` or `~/.codex` |
| Doc session: edit files, commit, push and open a Draft PR, discard | A newly created linked worktree and a `docs/<slug>` branch | Only human-written docs in `docs/` are writable; generated targets, generated regions, instruction files, and source are read-only; can send follow-up instructions to this session's agent and stop the current turn | Writing to main, merging; editing files outside the writable scope; the agent pushing or calling GitHub by itself |
| Clean worktrees: one-click clean, cleanup session, archive | Linked worktrees and local branches; leftover directories that git no longer registers; `docs/archive-<slug>` branches | Green items get one-click clean. Non-green items are authorized item by item in a cleanup session that you start: first archive the content worth keeping into `docs/archive/` (Draft PR), then delete. Each item is re-checked before execution | Deleting a worktree in use; deleting without authorization, or after the content changed since authorization; credential files going into `docs/`; deleting remote branches; the agent archiving or deleting by itself |

- Sending a message to a task owner goes to the Bot. The existing entry point is the CLI `repo-harness fleet message send`, which requires admission and claim context. The console shows task inbox messages and delivery receipts read-only.
- Coding sessions are not connected to the console: no sending messages to, stopping, or injecting content into sessions in the user's harness.
- Host projection (install, update, profile switching) and registry cleanup still only get commands, which the user runs in the terminal.
- Every write request must pass the Origin / Sec-Fetch-Site check and a write token. The page response delivers the token in an HttpOnly, SameSite=Strict cookie. The session sandbox forbids connections to the loopback address, so the agent cannot get the token and cannot call the write API. Other local processes have the same rights as the user, and the server cannot tell a human click from a program call. So the authorization for a non-green item is bound to the digest of the content-to-lose that you saw. The CLI must get a terminal confirmation before it deletes non-green items, and refuses in a non-interactive environment. Failures show the specific reason in the UI and never pretend to succeed.
- Browser payloads still contain no absolute paths, stderr, or environment variables. Doc session conversation text is new visible content and conflicts with the existing N4 (no terminal text, prompts, or tool arguments shown); see gap G3.

All constraints to revise change at once in phase 0. Slice 0.2 is accepted against this table:

| Constraint | Location | Change to |
| --- | --- | --- |
| I1, I2, I9: the console is read-only, zero write routes, the UI triggers no actions | Revamp plan §2; `operator.md` §3.1 items 1 and 6 | Allow the three writes in the table above; everything else stays read-only |
| "No writes", "no approval buttons" | Kumo plan non-goals | Add buttons only for the three writes in the table above |
| N4: no terminal text, prompts, or tool arguments shown | Kumo plan | Doc sessions show message bodies, tool category, relative paths, and execution status (G3); everything else stays hidden |
| "Docs show paths only, the server returns plain text only" | Revamp plan :251, :530 | The browser renders markdown, with raw HTML off and no scripts run |
| "Do not add `@xyflow/react` and `@dagrejs/dagre`" | Revamp plan §11 #1 | The architecture canvas can add them (open question 8) |
| Non-goals: mutation, starting Agent processes, SSE/WebSocket, and so on | `docs/design/DESIGN-local-human-control-board-v1.md` | Replaced by the new `docs/design/DESIGN-<slug>.md` |
| Read-only note | `README.md` | Changed to the three bounded writes |
| Empty write route list, non-GET returns 405, the UI has no forms | `operator-write-boundary.test.ts`, `operator-serve.test.ts`, UI tests | Rewritten item by item, with the reason for each explained in the PR |

## Write API

The three writes share one POST channel. Each request first passes the same-origin and token checks, then schema, idempotency, lock, and precondition checks, and is finally executed by the effect shared with the CLI. If the intent audit cannot be written, the write is not executed.

| Endpoint | Request body | Success | Failure codes |
| --- | --- | --- | --- |
| `POST /api/v1/settings/agents` | `request_id`, `expected_revision`, `changes[{runtime, enabled, uses}]`, `default_docs_runtime` | 200, the new `config_revision` and the keys actually changed | 409 `revision_conflict`; 422 `use_not_supported` (review accepts only claude, codex); 503 `busy` |
| `POST /api/v1/sessions` | `request_id`, `kind: docs \| worktree_cleanup`, `runtime`; docs also carries `repository_id`, `citations[]`, `instruction` | 201, `session_id`; docs also returns the branch name and worktree directory name | 409 `citation_stale`; 422 `runtime_not_enabled`; 501 `platform_unsupported`; 503 `busy` |
| `POST /api/v1/sessions/{sid}/messages` | `request_id`, `text`, `when: after_turn \| now` | 202, `landed: prompted \| queued \| steered` | 409 `steer_unsupported`, not silently changed to queued; 409 `session_closed` |
| `POST /api/v1/sessions/{sid}/stop` | `request_id` | 202, the current turn ends as `aborted`, the session is kept | 409 `no_active_turn` |
| `POST /api/v1/sessions/{sid}/commit` (docs) | `request_id`, `expected_head`, `expected_diff_sha256`, `message` | 200, commit, push result, and Draft PR link; on a failure part way, returns the steps already done | 409 `diff_changed`; 422 `path_outside_scope`; 422 `generated_region` |
| `POST /api/v1/sessions/{sid}/discard` (docs) | `request_id`, `expected_head`, `expected_loss_sha256` | 200, worktree and local branch deleted | 409 `turn_active`; 409 `loss_changed`; 409 `branch_pushed`, a pushed branch only gets a command |
| `POST /api/v1/worktrees/cleanup` | `request_id`, `expected_digest`, `ids[]`; non-green items also carry `session_id` and `approvals[{id, loss_sha256, plan_sha256}]` | 200, a result per item: archived (PR link), deleted, or skipped with the reason | 409 `digest_changed`; 409 `loss_changed`; 422 `not_approved`; 422 `in_use` |

Check order. If any step fails, nothing further runs:

1. Host matches exactly (existing, 421).
2. Origin must be present and equal to this service (POST only; GET keeps "check only if present").
3. `Sec-Fetch-Site` must be `same-origin`.
4. The route must be in `OPERATOR_ROUTES` and marked `write:true`. The dispatcher allows POST only for these routes; other methods still return 405. The identity check comes before routing (`operator.md` §3.1 item 2).
5. `Content-Type` must be `application/json`, the body is at most 64 KiB, and it is read against a deadline.
6. The write token is in the HttpOnly, SameSite=Strict cookie that the page response sets. The server compares it in constant time. The token is regenerated on every serve start.
7. The body is parsed with a closed decoder; unknown fields are rejected outright (`operator.md` §3.1: one schema, one decoder).
8. `request_id` is a UUID, bound to the operation, the target, and the request body digest. The same id with different content returns 409 `request_mismatch`. Duplicate requests return the stored result. If the action ran but the result audit was not written, the status is "pending reconciliation" (待核对). The UI shows pending reconciliation. It does not report "not executed" and does not replay automatically (`references/bot-control.md`).
9. Lock per target: one lock for the config file, one per doc session, one per repository for session creation, and one worktree topology lock per repository (`withWorktreeTopologyLock`). Reuse `exclusive-directory-lock.ts`.
10. Check preconditions: config revision, worktree HEAD, the diff hash the user saw, the content digest of the discard list or cleanup authorization that the user confirmed, and no active turn. A mismatch returns 409.
11. Write the intent audit first, then execute, then write the result audit. All console writes are recorded in `~/.repo-harness/operator/audit.jsonl`, not in the worktree's evidence ledger: a new worktree has no genesis record, and discard and cleanup also delete it. If the intent audit cannot be written, the write is not executed.
12. All errors use `{error:{code,message,next_action}}`, no longer a bare `{code}`.

- **CLI parity**: every write gets a CLI command first; HTTP is only a thin wrapper, sharing the same effect and builder (I7). The Bot uses the CLI, the console uses HTTP, and the results are the same.
- **Constraints to change**: see the constraint table in "Write and Permission Boundaries".
- **Routes and tests to change**: the write route list in `operator-write-boundary.test.ts` changes from an empty array to the 7 above, and the method scan adds POST. The new GET routes (docs tree and body, session events, worktree list and stable ids) go into `OPERATOR_ROUTES` and the route list test. The 405 cases in `operator-serve.test.ts` and the "no forms" assertions in the UI tests are rewritten one by one, with the reason for each explained in the PR.
- **Design brief gate**: `ux-feature-guard` requires a confirmed `docs/design/DESIGN-<slug>.md` before frontend work starts.

## Technology Choice

Conclusion: keep React. The pressure points this time are data sources and the write boundary, not rendering performance. Switching frameworks would mean rewriting the existing 4.1k lines along with the Kumo component library.

| Dimension | React (current) | Solid 2.0 |
| --- | --- | --- |
| Release status | Stable | Still RC: latest is 2.0.0-rc.9, 2026-09-18, no stable release ([releases](https://github.com/solidjs/solid/releases)) |
| Existing code | `src/operator-web` has 23 .tsx files, already wired to Vite, Tailwind v4, and tests | Full rewrite |
| Component library | `@cloudflare/kumo` is a React component library; the Kumo plan is approved | No Kumo; build our own or switch libraries |
| OAR integration | `@botiverse/oar/browser` and `/observe` have only pure reducers and types, no network client; the server sends records to the browser and the frontend folds them, which works for both | Same as left |
| Streaming conversation updates | Relies on bucketed rendering, virtual lists, `useSyncExternalStore` | Fine-grained reactivity fits naturally; this is its only clear advantage |
| Canvas (architecture diagrams) | `@xyflow/react` 12.12 + `@dagrejs/dagre` 3.1 (both MIT) are usable but need separate approval under the dependency rules; elkjs is EPL-2.0 or GPL-3.0 and is excluded | Few library options |

- Trigger for re-evaluation: the doc session page shows measurable rendering lag on real data, and neither bucketing nor virtual lists fixes it.
- This follows the repo rule: prefer installed dependencies, and do not add layers for pressure we have not observed.

## Storage Levels: repo and global

Re-home by one rule. Content that must evolve in the same commit as the code and be reviewed in a PR goes in the repo and is committed. Run records that belong to only one checkout go in the repo's ignored area. Content that belongs only to this machine or this user and is shared across repositories goes in global. Anything that can be recomputed from another source is a cache, never an authority. By this rule, most directories do not move. The real work is to retire the dead parts and to unify global under one root.

### CLI Inventory (G18)

The CLI page lists all command-line tools installed on this machine, not only the few used for development. Vibe coders often install many CLIs and forget to remove the unused ones. For each CLI the page gives its source, version, disk use, last use, GitHub link, and stars. It marks the unused ones and gives an uninstall command for the user to run in the terminal. The console does not uninstall.

| Item | Approach |
| --- | --- |
| Inventory | The background collector reads the read-only lists of each package manager. It lists only packages that you installed on purpose and that have an executable (Homebrew uses installed-on-request); dependencies pulled in by other packages are not listed separately: Homebrew formulae and casks; global packages of npm, pnpm, and bun; pipx, uv tool, cargo install, mise; for go install, the module path in `go version -m`; on Linux, also the installed packages of apt, dnf, and apk. The locations used by official install scripts (such as `~/.local/share/claude`, `~/.codex/packages/standalone`, `~/.opencode/bin`, `~/.fly`, `~/.railway/bin`) are mapped to their tools by the seed catalog. The other executables on PATH are mapped to a source by their real path; those with no match are marked "Manual install" (手动安装). Project devDependencies (wrangler, and the install method that supabase officially recommends) are not on PATH and are not listed; files in the system directories /usr/bin, /bin, /usr/sbin are not listed either |
| Version and disk use | The version comes from the package manager's record; the collector does not start each CLI to build the list. Disk use is du of the package directory, run at low frequency and cached by mtime |
| Last use | repo-harness hooks already see the commands that agents run. Hook events get one new field that records only the command name and the time, not the arguments. Shell history is not read by default; when it is on, only counts are kept. File atime is only a hint |
| Unused | By default: not used by an agent or (when on) in shell history for 90 days, and not a dependency of another package |
| GitHub and stars | The repository address first comes from local package metadata: Homebrew homepage and download URL, npm repository, PyPI project\_urls, crates.io repository. If the metadata has none, match the package name or install location against the seed catalog. When a command name maps to several repositories (such as `asc`, `kimi`) and the package name does not match, list the candidates and give no stars. Stars are queried with gh under the user's own login, follow repository redirects, and are cached for 24 hours; a monorepo is marked "Whole repository" (整个仓库). If nothing is found, give only the official website link |
| Upstream status | Mark repositories that are archived (gh `archived`), packages that are deprecated or archived (npm `deprecated`, PyPI project status), and repositories that moved; if such a CLI is in use, also suggest a reinstall. Examples: the neonctl repository was archived on 2026-06-25 and the CLI moved into neon-pkgs; kimi-cli on PyPI is archived, and its successor is kimi-code |
| Sign-in status | Run only for CLIs that have a read-only status command (such as `gh auth status`), and return only the account name; CLIs that are unused but still signed in are marked separately |
| Uninstall | One command by source: `brew uninstall`, `npm rm -g`, `pnpm rm -g`, `bun rm -g`, `pipx uninstall`, `uv tool uninstall`, `cargo uninstall`. For script installs, use the vendor's uninstall command (such as `opencode uninstall`); if the vendor gives none, give the location of the binary and of the PATH line in the shell rc. Prerequisite steps and sign-out that the vendor requires come before the uninstall (such as `stripe plugin uninstall --all`). Config and sign-in directories (such as `~/.claude`, `~/.codex`, `~/.config/stripe`) get a separate command and are not merged into the uninstall. No command for packages that other packages depend on; for manual installs, give only the directory |

- **Why commands only**: uninstall is deletion, which is a hard boundary; package managers also run the package's own scripts during uninstall.
- **Privacy**: the inventory stays only on this machine. Only the deprecation status and star queries use the network, and they send only package names and owner/repo, never local paths or command records. Uninstall commands are generated from source templates: fixed paths in a template are shown as is, local paths that were found are shown only when they start with \~, and all other paths are replaced with \[private path\] by the existing local path filter.

## Docs and Architecture Management

The Docs page lets people read docs, cite passages, and hand them to an agent to edit, with changes coming back as a Draft PR. The Architecture page draws the model as a base map and overlays today's changes, violations and drift, PR impact, test coverage, and decision layers. The agent only writes docs; source is read-only in the session.

### Doc Reading (G7)

- `GET /api/v1/repositories/{id}/docs/tree` returns `path`, `size`, and `sha256` for readable files. `GET …/docs/file?path=` returns the body, HEAD commit, file sha256, and whether there are uncommitted changes.
- The body is read from the blob in the latest commit on the default branch, which is the same starting point as the doc session. At service start, each repository gets one long-running `git cat-file --batch` worker (with a timeout). GET only asks it for objects and spawns no other subprocess. Files with uncommitted changes in the working tree are still shown, marked "Citations use the committed version" (引用以提交为准). Single-file limit is 512 KiB.
- Scope: the allowlist is `docs/**` plus cited source files. Resolve the realpath first, then check both the allowlist and the denylist on the physical path. MCP's `paths.ts` checks only the logical path, so symlinks can escape scope; it cannot be reused as is.
- An existing convention must change: the revamp plan requires "docs show paths only, the server returns plain text only" (:251, :530). The new proposal renders markdown in the browser; the server still returns only the raw text. Rendering runs no scripts: raw HTML is off, and links allow only http, https, and relative paths inside the repository. Mermaid uses the strict security level, and the generated SVG is shown as an image. No innerHTML is used, so the existing scan tests stay valid.

### Citation Protocol (G8)

- Citation = `{path, start_line, end_line, range_sha256, file_sha256, commit}`. The browser maps the rendered selection back to source file line numbers; `range_sha256` is the hash of those lines' raw bytes.
- When a session starts, the server re-reads the file at the session's starting commit. If the hash of the content at those line numbers matches, it passes. If the file changed but the original text appears exactly once elsewhere, it switches to the new line numbers and marks this in the UI. If neither holds, it returns 409 `citation_stale` and asks the user to cite again. MCP matching `oldBlock` by line offset and recording a fragment hash is the same idea.
- Source citations are read-only context only, limited to files inside the repo that are not ignored and not on the denylist.

### Doc Session (G5)

1. **worktree**: create a linked worktree from the latest commit on the default branch, with branch name `docs/<slug>`. The directory goes under the repo-harness managed worktree root (`REPO_HARNESS_WORKTREE_ROOT`, the system temp directory by default) with the `<repo>-wt-` prefix, so the existing sweep can manage it.
2. **Host**: a new docs host, based on the coding host deleted in #932 plus the review host's isolation. The review host's profile is `(allow default)`: it only forbids writes and leaves reads and network open. The docs host must be tighter. It first uses a zero-model test to prove that a subprocess cannot write, read, or connect to the forbidden areas, and only then opens the session:
   - Write: open only the human-written docs in `<worktree>/docs/**` and the temp directory. The generated targets that the projection manifest lists, `.git`, AGENTS.md, CLAUDE.md, settings and credential files, and the hooks, skills, commands, and prompts directories are all write-protected.
   - Read: credential files and directories (gh config, `~/.codex/auth.json`, `~/.repo-harness/mcp.tokens.json`, and so on) and `.env`-type files are read-protected.
   - Environment: the session uses a private HOME, CODEX\_HOME, and CLAUDE\_CONFIG\_DIR that contain only copied-in model credentials, the same way as the review host's `prepareCodexHome`. GH\_TOKEN and the git credential helper are removed.
   - Network: only the model API of that runtime is kept. The loopback address and other local services are all refused, so the agent cannot call the console's write API.
   - Subprocesses: inherit the same boundary; the programs that can start are on an allowlist.
3. **Agent startup**: OAR always starts in no-confirmation mode (Claude with the bypass flag, Codex as danger-full-access), and can only run within the OS boundary above. Per `CLAUDE.md`, this kind of confirmation bypass needs the user's item-by-item approval (open question 3). Runtimes whose isolation is not verified are not enabled. If the boundary cannot be built, the session does not start and does not fall back to running without isolation.
4. **Events**: the session directory is `~/.repo-harness/operator/sessions/<sid>/`, outside the sandbox's writable scope. The host redacts first, then writes to disk, appending to `events.jsonl` (0600): message bodies, tool category, relative paths inside the repository, execution status, turn boundaries, and failure category. Message bodies also pass `SECRET_TOKEN_PATTERNS`. Raw tool arguments, full commands, terminal output, environment variables, and reasoning are not written to disk and not shown; a structured operation summary replaces them.
5. **Push**: the browser polls `GET /api/v1/sessions/{sid}/events?after=<epoch>.<seq>` by cursor, once per 1 s while active and once per 30 s when idle. The epoch increments on every host restart, because after OAR resumes a session `seq` restarts from 0.
6. **Commit**: done by the server's effect. The agent has no push permission and cannot get GitHub credentials. The server lists every change against the baseline (including untracked files) and confirms all are within the writable scope. It uses `repo-harness architecture-projection hand-edits --json` to confirm that no generated region was touched; if one was touched, it returns 422 `generated_region`. It checks `expected_diff_sha256`. After the user sees the full diff, the user clicks "Commit, push, and create Draft PR" (提交、推送并创建 Draft PR) once. Each of the three steps gets its own audit record. On failure, the UI shows the step where it stopped. A retry continues from that step, and does not commit twice or open the PR twice.
7. **Discard and cleanup**: "Discard" (丢弃) first stops the current turn, then lists the content that will be lost: uncommitted and untracked files, and unpushed commits. It computes a content digest of this list. After the user confirms, the server recomputes it under the lock. If the list or digest changed, it returns 409 `loss_changed` and deletes nothing. A merged worktree is not deleted by the session itself; the existing closeout and sweep (`cleanupExactWorktree`) handle it, also with an audit record. A pushed branch only gets a command. This matches the deletion rules in `CLAUDE.md`.
8. **Platform**: Linux and Windows return 501 `platform_unsupported` until they have a matching OS boundary. The read-only console works on all platforms.

_Diagram: doc session states — 6 states, 2 human confirmations; see the design canvas._

The host loops between "Running" (运行中) and "Waiting for your review" (等你审阅). There are only two ways out of this loop, commit and discard, and both need a human's approval.

### Architecture (G11, G22, G27)

Four base maps (layers, sequence, topology, modules) are enough; no new views are added. The rest of the big-company architecture SOP either becomes a layer on a base map, fed by automated checks, or is not done. Every day, humans look at the lit-up parts of the base map: which modules today's merges touched, where the violations are, and which step of which flow a PR affects. The console now has only a module list and a one-hop dependency graph (`ModuleGraph.tsx`); the other three base maps exist only in the design.

- **Base map**: nodes and edges come from `export native`. Node size is the line count of the files under the node (git file list plus `resolve --paths-from` ownership). Edge thickness between capabilities is the import count from `deps --json`. Edges between components have no thickness difference, and archctx does not yet output call counts. The console computes the layout (G11). The module base map and "Today's changes" open by default.
- **The layer base map waits for #408**: per ADR-0049 ([#402](https://github.com/Ancienttwo/arch-context/issues/402)), 0.9.3 sorts only by name, so core would be drawn above effects, and the layer direction cannot be checked.
- **The page is read-only**: clicking a lit-up node opens a drawer that lists the changes, PRs, violations, and fix commands. Model changes are made by the agent through the ChangeSet flow in the user's own harness; the console only shows the gaps (open question 4).
- **Refresh**: the collector calls only stateless commands: `export native`, `resolve`, `deps`, `debt`, `flows check`, `docs anchors`. When the index is missing or stale, the layer shows "Unknown" (未知), and the collector does not build the index.
- **Model completion (G27)**: fill in `layer` for nodes. Add external system nodes for GitHub, npm, each agent CLI, and so on. Add topology nodes from the storage and process topology section of `current-architecture.md` and from the code. ## Worktree Management

The Worktree page draws the disk usage of all worktrees on this machine as one chart, in three colors by whether they can be deleted. The "Reclaimable" (可回收) kind can be cleaned with one click. For the rest, you start a cleanup session: the agent investigates and gives keep-or-delete recommendations and an archive plan, and after you authorize item by item, the server archives first, then deletes. Age alone is not a reason to delete; the worktree lifecycle research set this invariant.

| Category | Condition | Page shows | Action |
| --- | --- | --- | --- |
| Reclaimable (green) | The same judgment as `contract-worktree sweep`: under the managed root, with the `<repo>-wt-` prefix in the directory name; the branch has its own commits and they are merged (ancestor, or absorbed and reachable on the remote); the working tree is clean, and the only ignored files are rebuildable (such as `node_modules`, build output); no unpushed commits; not locked; no active-worktree marker points to it; the task run record is closed; not the cwd of the current session; no process uses it | Counted in "Reclaimable space" (可回收空间) | One-click clean, or copy the command |
| Needs your authorization (yellow) | Everything else that is not green and not in use: not merged (PR closed, branch deleted, or still open); uncommitted changes or unpushed commits; the branch has no commits of its own; ignored files that are not rebuildable (such as `.env`, `_ops/`, `.ai/harness/handoff/`); locked or has an active-worktree marker; leftover directories that git no longer registers; worktrees under other tool roots (`~/.codex/worktrees/`, `<repo>/.claude/worktrees/`) | Lists what would be lost: count of unpushed commits, count of uncommitted and ignored files | You start a cleanup session; the agent gives keep-or-delete recommendations and an archive plan; after you authorize item by item, the server archives first, then deletes |
| In use (red) | A process uses it, it belongs to a running session, or it is the cwd of a session | Shows the reason it is in use | No delete entry point; when no longer in use, it becomes green or yellow |

- **Inventory**: `git worktree list --porcelain` for each registered repository, which the Dev Activity collector already runs. Then scan the known roots for leftovers that git no longer registers: `<repo>-wt-*` under the managed root, `/tmp/repo-harness-mcp-worktrees/`, `<repo>/.claude/worktrees/`, `~/.codex/worktrees/`. The old location `../<repo>-wt-*` next to the primary checkout is cleaned once by [#984](https://github.com/Ancienttwo/repo-harness/issues/984). The browser gets only directory names, not absolute paths (N4).
- **Origins and records**: there are three record sets now. `contract-worktree start` writes `.ai/harness/worktrees/<slug>.json` in the worktree (plan, branch, source repository, baseline commit, start time), and while in use there is also an `.ai/harness/active-worktree` marker. MCP records in `~/.repo-harness/mcp-workspaces.json`. Task agents leave a binding in `.ai/harness/runs/task-workspaces/` of the primary checkout and write `closed.json` when they finish. The herdr-portal skill and hand-opened `/tmp/<repo>-wt-<slug>` at the default path leave no record and can be identified only by name and git topology. Worktrees that Claude Code and Codex open themselves are managed by each tool. Codex CLI never cleans up automatically, so it piles up the most.
- **Unified record (G26)**: every repo-harness creation path, including the portal skill, writes the same record: creator, purpose, linked task or PR, creation time; closeout writes the end state. The cleanup session investigates non-green items by this record.
- **Judgment**: green reuses the sweep predicate directly (`src/effects/state/coordination-worktree-topology.ts`) instead of writing another one. Merge uses ancestor and absorbed from `scripts/worktree-merge-lib.sh`. Dirty and unpushed come from `git status --porcelain=v2 --branch`, and ignored files are listed separately. PR status comes from Dev Activity. Owning processes are checked by cwd. All of this runs in the background collector, with timeouts. The board's "worktree not cleaned yet" uses this judgment, Dev Activity's `cleanup_pending` is retired, and only one merge judgment stays.
- **Size**: `du` runs in the background at low frequency, with a timeout, cached by directory and mtime. Linked worktrees share the object store, so the bulk is usually `node_modules` and build output.
- **One-click clean (G24)**: `POST /api/v1/worktrees/cleanup`, with a body of `request_id`, `expected_digest`, and the stable ids that the server issued; no paths are sent. Under the topology lock, the server re-checks each item by the same rule, then deletes with the existing exact-delete primitive. Items that no longer meet the conditions are skipped and reported. One-click clean accepts only green items. Non-green items need the authorization from a cleanup session. When the CLI deletes non-green items, it also needs an item-by-item confirmation in the terminal, and refuses in a non-interactive environment. Merged local branches are deleted together. Every run writes an audit.
- **Cleanup session (G25)**: you click "Let the agent clean up" on the Worktree page to start a session of type `worktree_cleanup`. It shares the host, events, and review flow with doc sessions. Inside a read-only OS boundary, the agent investigates non-green items: whether the commits are still on the remote, whether the PR is closed, and whether uncommitted and ignored files are rebuildable build output. Patch similarity is only a hint, not proof of merge. Then it hands in a plan. For each item the plan states delete or keep, the reason, the evidence, what would be lost, and where content worth keeping is archived. The page compares the disk chart before and after cleanup. Green items are checked by default. Yellow items are unchecked by default; you check them one by one after you see the evidence and what would be lost, and that check is the authorization. Red items have no delete entry point. A closed PR or a deleted remote branch does not mean the local content can be lost, so yellow items are unchecked by default. The agent itself archives nothing and deletes nothing.
- **Execution after authorization**: after you click "Authorize and run" (授权并执行), the server re-checks each item. Green items are deleted by the rule. Yellow items are first archived per the plan, then deleted, and only if the digest of the content to lose matches what you saw; if it changed, the item is skipped and needs re-authorization. Red items are always skipped. Deletion reuses the sweep's recovery area and receipts (`cleanupExactWorktree`), with a new authorized mode that can delete dirty and unmerged worktrees and leftover directories that git no longer registers. Local branches are deleted together with the authorization. Remote branches are not touched.
- **Archive**: content already in git history (pushed or merged commits) needs no archive, because it can be recovered from history. What needs archiving is content that is uncommitted, unpushed, or ignored but worth keeping. It all goes into `docs/archive/<date>-<worktree>/`: docs keep their original relative paths; unpushed commits are saved as patches with `git format-patch`; one `SOURCE.md` in the directory records the repository, worktree, branch, baseline commit, original path, and cleanup session id. The server uses the same commit flow as doc sessions: commit to a `docs/archive-<slug>` branch, push, and open a Draft PR. The worktree is deleted only after the push succeeds. The archive is in git history, so later you can trace its source by `SOURCE.md` and the commit record. Credential files (`.env` and similar) do not go into `docs/`. To keep them, the server moves them unchanged to `~/.repo-harness/archive/<repo-key>/` with permission 0600, and does not read or show their content. Large binary files also go there, and `SOURCE.md` records their sha256.
- **CLI parity**: add `repo-harness worktrees list --json` and `repo-harness worktrees clean --ids … --expected-digest …`, which cover all origins; the existing `contract-worktree sweep` handles only the set that repo-harness opened itself.
- **Prevention**: the contract's closeout already deletes merged, clean worktrees, and the page shows which closeout did not run. Home's today summary adds one line for reclaimable space. The worktree root is unified in the system temp directory per [#987](https://github.com/Ancienttwo/repo-harness/issues/987): [#983](https://github.com/Ancienttwo/repo-harness/issues/983) changes the template to `{{system_tmp}}`, and [#985](https://github.com/Ancienttwo/repo-harness/issues/985) blocks `git worktree add` outside the root. The console does not set up its own root. Notifying the owning agent to close out after a merge is in [#993](https://github.com/Ancienttwo/repo-harness/issues/993).

## Open Questions and Milestones

The recommendation for each item below comes from an independent Codex review. Check each one after you confirm it. Writes are off by default and open one at a time, in this order: local config, doc sessions, worktree cleanup. Delivery is in six phases.

- [ ] Approve the three bounded writes and revoke the read-only constraints in place since #482 (I1, I2, I9)? (G1) Recommendation: yes, but keep read-only as the default, and open them one at a time in this order: local config, doc sessions, worktree cleanup.
- [ ] How much should the doc session page show? (G3) Recommendation: message bodies, tool category, relative paths, and execution status. Raw tool arguments, full commands, terminal output, and environment variables are not shown; a structured operation summary replaces them, and redaction happens before writing to disk.
- [ ] Should doc sessions accept OAR's no-confirmation startup (the default for every runtime; Claude's bypass flag cannot be turned off)? (G5) Recommendation: yes, with conditions. Besides writes, the OS boundary must also narrow sensitive file reads, environment variables, network egress (including loopback), and subprocesses. GitHub credentials stay only on the server. Runtimes whose isolation is not verified are not enabled. If the boundary cannot be built, do not fall back to running without isolation.
- [ ] Writable scope for doc sessions? (G5) Recommendation: in the first version, open only the human-written docs in `docs/`, excluding generated regions and instruction files. Do not open `plans/` and `.archcontext/model/` for now, and do not move directories to unify permissions. Model changes still go through the user's own harness and ChangeSet.
- [ ] Should the console open doc session PRs directly, or only give a command? Recommendation: the console opens them directly. After the user sees the full diff, the user clicks "Commit, push, and create Draft PR" once, and the server runs it. The agent has no push permission. On failure, the UI shows the step where it stopped, and does not commit twice or open the PR twice.
- [ ] Is it OK for the first version of doc sessions to support only macOS? (G5) Recommendation: yes, only for doc sessions; the read-only console works on all platforms.
- [x] How is worktree cleanup authorized? (G24, G25) Decided (your decision, replacing Codex's recommendation of "the first version deletes only green items"): green items get one-click clean. For non-green items you start a cleanup session, and the agent gives keep-or-delete recommendations and an archive plan. After you authorize item by item, the server first archives the content worth keeping into `docs/archive/`, then deletes.
- [ ] Approve the new dependencies: `@xyflow/react` and `@dagrejs/dagre` for the architecture canvas, and a markdown rendering library (such as `react-markdown`, `remark-gfm`) and `mermaid` for doc reading? (G7, G11) Recommendation: yes, used only in these two places. Verify the exact versions and licenses at implementation time. Keep React + Kumo, and do not switch frameworks.
- [ ] Should tests be management only, or also allow agents to write tests? (G20, G21) Recommendation: only inventory, results, and commands. Do not open sessions that write tests, and do not run tests in the UI. No result never shows as passed. "red→green" needs two pieces of evidence: a comparable baseline failure and a pass after the fix.
- [ ] Should Bots go back to dispatching work over MCP? (G30) Recommendation: no. The PM/Bot MCP was deleted in 0.23.1. Dispatch goes only through CLI → herdr, and MCP lets Bots read status and write plans and reviews. When a Bot is not on the machine that runs herdr, put an executor on that machine instead of opening MCP dispatch.
- [ ] Should Bot-to-Bot Slack conversations go into repo-harness? (G31) Recommendation: do not read Slack. The herdr plugin cannot receive inbound messages. repo-harness only sends events with repository and task ids to the channel, and the Bots coordinate in the channel themselves. One task still has only one owning Bot.
- [x] Does the dark theme replace the warm paper color, or do both coexist? Decided: both coexist, with light Paper as the default (G13)
