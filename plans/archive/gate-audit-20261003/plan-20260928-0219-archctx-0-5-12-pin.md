### Data Flow
`src/cli/commands/global-runtime.ts`'s `runGlobalRuntimeSetup` resolves and validates one Bun
executable (`resolveBunExecutable` + `ensureSupportedBunRuntime`), then hands it to
`installAgentFleet(sourceRoot, bunExecutable, env)`, which sets `REPO_HARNESS_BUN_BIN` on the child
env before invoking `scripts/install-agent-fleet.sh`. The helper's `BUN_CANDIDATES` selection reads
that variable first and, when set, uses it exclusively — it only falls back to `command -v bun` plus
`${HOME}/.bun/bin/bun` name discovery for a standalone invocation that received no handoff.

## P1 Map

The archctx pin surfaces are the same five named by the 0.5.9 precedent
(`tasks/notes/20260910-0134-archctx-0-5-9-pin.notes.md`): `package.json`/`bun.lock`,
`ARCHCTX_REQUIRED_VERSION`, `REFACTOR_PROVIDER_VERSION`, the generated policy defaults and their
seeders, and the AXR clean-room drivers plus version-bound test fixtures. The Bun-handoff surface is
independent: `scripts/install-agent-fleet.sh` (+ its `assets/templates/helpers/` projection) is the
only consumer of `REPO_HARNESS_BUN_BIN` for fleet installation, and
`src/cli/commands/global-runtime.ts`'s `installAgentFleet` is its only producer inside this repo's own
runtime-setup path. `tests/install-agent-fleet.test.ts` is the sole test file exercising the helper's
Bun-version-resolution behavior directly via `spawnSync`.

## P2 Trace

A validated Bun executable is resolved once in `runGlobalRuntimeSetup` (`resolveBunExecutable` +
`ensureSupportedBunRuntime`), then threaded as a plain string parameter into `installAgentFleet`,
which is the only call site that sets `REPO_HARNESS_BUN_BIN` on the child env before invoking the
helper script. Inside the script, `BUN_CANDIDATES` reads that variable first: if set, it is the only
candidate considered, and an unsupported handed-off Bun fails the whole helper closed with
`requires Bun >= 1.4.0 (found: ...)` — it never falls through to `command -v bun` or
`${HOME}/.bun/bin/bun`. `tests/install-agent-fleet.test.ts`'s two existing Bun-version tests spawn the
script directly with `env: { ...process.env, HOME, PATH }`, which leaks the invoking shell's own
`REPO_HARNESS_BUN_BIN` (if any) straight into that same first-priority slot, silently pre-empting the
PATH/HOME discovery path the tests exist to prove.

## P3 Decision

Move the pin and require no new feature, because the installed 0.5.12 package's own capabilities
handshake proves the feature set is unchanged from 0.5.11 — adding a required feature here would be
inventing a gate the upstream package does not need. Close the two Bun-handoff test gaps by clearing
the leaking env var (gap A) and adding the missing fail-closed-branch test (gap B), both proven with
real red/green runs rather than static reasoning about the script. Record, rather than fix, the
sibling Bun-by-name call sites: `init.ts`'s sync-skill path has no validated-Bun variable in scope at
all, so extending `b87c7f39`'s exact pattern there would be inventing a design, not copying one — that
decision belongs in its own slice.
