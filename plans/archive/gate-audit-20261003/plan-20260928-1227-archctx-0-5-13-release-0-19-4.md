## Approach
### Strategy
Pin archctx/archctx-contracts to the published 0.5.13 release across every pin surface named by the
0.5.9 and 0.5.12 precedents, confirm the capability set did not move across 0.5.11→0.5.12→0.5.13 so
`ARCHCTX_REQUIRED_FEATURES` needs no companion change, and confirm archctx 0.5.13's RPC error-shape
change (developer-review methods now return HTTP 200 `AC_SCHEMA_INVALID` instead of HTTP 500) does not
affect any repo-harness code path. Then prepare the 0.19.4 release metadata — package/skill/template
version, five README stamps, a changelog entry covering both archctx pins and the fleet Bun-handoff
fix from #455, and a new release checklist — following the 0.19.3 precedent's exact file set. Close
with this plan/notes pair as the diff-bound task-sync evidence CI's Governance gate requires.

### Data Flow
`package.json`'s two dependency literals and the regenerated `bun.lock` integrity hashes are the
registry-facing pin; `ARCHCTX_REQUIRED_VERSION` (`src/core/architecture/projection.ts`) and
`REFACTOR_PROVIDER_VERSION` (`src/core/refactor/policy.ts`) are the two runtime-facing constants the
architecture-projection and refactor providers assert against during their capability handshake with
the installed `node_modules/archctx/bin/archctx.mjs` binary. The generated policy defaults
(`.ai/harness/policy.json` and its two seeders) hand the same version/feature pair to freshly
initialized repos. On the release side, `package.json`'s top-level `version` field and
`assets/skill-version.json`'s `version`/`templateVersion` fields are the two authorities the five
README "Current Release" stamps and the generated workflow stamp (`repo-harness@{version}+template@{templateVersion}`) quote; `check:hooks`/`check:helpers`/`check:reference-configs` verify no
generated projection drifted out of sync with either bump.

## P3 Decision

Move the pin and require no new feature, because the installed 0.5.13 package's own capabilities
handshake proves the feature set is unchanged from 0.5.12 (and from 0.5.11 two pins back) — adding a
required feature here would be inventing a gate the upstream package does not need. Confirm, rather
than assume, that 0.5.13's RPC error-shape change (developer-review methods now return HTTP 200
`AC_SCHEMA_INVALID` instead of HTTP 500) does not affect repo-harness: it doesn't, because
repo-harness's only integration surface with archctx is the CLI capabilities/projection/refactor
subprocess handshake, never the daemon's `developerReview.*` RPC methods that surface changed. Bump
the release straight from the last published `0.19.2` to `0.19.4` rather than backfilling a `0.19.3`
publish, because repairing that gap is a separate decision outside this dispatch's scope — stating it
plainly in the release checklist is more honest than silently treating `0.19.3` as if it had shipped.
