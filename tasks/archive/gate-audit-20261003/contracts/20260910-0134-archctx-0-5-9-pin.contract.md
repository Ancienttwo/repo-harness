## Why

Under archctx 0.5.8 the projection result field `priorCommittedApplies` does not exist, so a
provider that never carries it and a provider that silently drops it produce the same receipt: a
late write committed by a killed attempt stays undeclared with no version signal. archctx 0.5.9 is
published with the capability flag `projection-prior-committed-applies-v1`, so the consumer can
now require that signal and fail the capabilities handshake closed without it.

## Goal

Every archctx / archctx-contracts pin surface in this repository resolves exactly 0.5.9 --
including the seeders under `scripts/`, which ship inside the npm package and therefore reach
every generated repository -- and `ARCHCTX_REQUIRED_FEATURES` includes
`projection-prior-committed-applies-v1`, so a 0.5.9 capabilities payload that omits the feature
is rejected before any projection request is sent.

## Acceptance Notes (Human Review)

- Functional behavior: every archctx pin surface resolves 0.5.9 and the capabilities handshake
  requires `projection-prior-committed-applies-v1`.
- Edge cases: a 0.5.9 payload missing the feature is rejected; the refactor stage pins move with the
  package so package-local resolution still finds the installed CLI.
- Regression risks: a stale global runtime resolving 0.5.8 against a 0.5.9 policy reopens the
  known publish-to-refresh window; package-local resolution is the mitigation already in place.
  A seeder left behind ships a policy the generated repo's own `readRefactorPolicy` rejects; the
  parity guard in `tests/create-project-dirs.runtime.test.ts` now runs the real seeders through the
  real readers so that class cannot recur silently.
