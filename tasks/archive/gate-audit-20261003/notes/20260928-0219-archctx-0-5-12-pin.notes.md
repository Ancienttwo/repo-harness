## Design Decisions

- The archctx/archctx-contracts pin (commit `6e0eafdc`) moves every pin surface from 0.5.11 to
  0.5.12: `package.json` + `bun.lock`, `ARCHCTX_REQUIRED_VERSION`
  (`src/core/architecture/projection.ts`), `REFACTOR_PROVIDER_VERSION`
  (`src/core/refactor/policy.ts`), the generated policy defaults
  (`.ai/harness/policy.json`, `scripts/ensure-task-workflow.sh` and its
  `assets/templates/helpers/ensure-task-workflow.sh` projection, `scripts/lib/project-init-lib.sh`),
  the AXR clean-room drivers (`scripts/axr5-archctx-clean-room.ts`,
  `scripts/axr6-stop-host-cycle.ts`, `scripts/axr7-consumer-e2e.ts`), and the version-bound test
  fixtures. This is the same pin-surface inventory the 0.5.9 precedent
  (`tasks/notes/20260910-0134-archctx-0-5-9-pin.notes.md`) enumerated; no new surface appeared.
- Capability decision: 0.5.11 and 0.5.12 advertise identical capabilities, so
  `ARCHCTX_REQUIRED_FEATURES` (and `REFACTOR_SCAN_FEATURES`/`REFACTOR_VERIFY_FEATURES`) are
  unchanged. Verified two ways: (1) `git show 6e0eafdc -- src/core/architecture/projection.ts
  src/core/refactor/policy.ts` touches only the version-literal lines, not the feature arrays; (2)
  real handshake against the installed 0.5.12 package —
  `node node_modules/archctx/bin/archctx.mjs capabilities --json` lists all 5 required features
  (`architecture-docs-renderer-v2`, `architecture-refresh-signal-v1`, `projection-apply-receipt-v1`,
  `projection-prior-committed-applies-v1`, `projection-protocol-v2`) among its 11 advertised
  features, and `bun src/cli/index.ts architecture-projection status --json` reports
  `"reason": "exact package-local capability handshake passed"`. Because capabilities did not move,
  this pin needed no companion required-feature change, unlike the 0.5.9 precedent.
- The fleet Bun handoff fix (commit `b87c7f39`, landed alongside the pin on this branch) hands the
  runtime's already-validated Bun executable to `scripts/install-agent-fleet.sh` (and its
  `assets/templates/helpers/install-agent-fleet.sh` projection) through `REPO_HARNESS_BUN_BIN`,
  because the helper previously re-discovered `bun` by name from `PATH`, silently skipping a
  validated executable that is not literally named `bun` (npm ships
  `node_modules/bun/bin/bun.exe`) and letting an older `PATH` Bun fail the version floor even when a
  supported Bun was already in hand.
- Gap A (test isolation): `tests/install-agent-fleet.test.ts`'s two Bun-version tests
  (`an unsupported Bun version fails before creating HOME state`,
  `a supported HOME Bun wins when PATH resolves an unsupported Bun`) spread `...process.env` into
  the child environment without clearing `REPO_HARNESS_BUN_BIN`. A shell that already exports a
  valid handoff Bun — exactly what a caller now does after `b87c7f39` — leaks through the spread and
  short-circuits the very `PATH`/HOME discovery these tests exist to exercise. Fixed by adding
  `REPO_HARNESS_BUN_BIN: ""` to both env objects, following the existing precedent at
  `tests/cli/fleet-offer-acquire.test.ts:215`.
- Gap B (missing coverage): no test covered the fail-closed branch `b87c7f39` introduced — a
  handed-off `REPO_HARNESS_BUN_BIN` below the version floor must fail the whole helper, even when a
  supported Bun sits at the fixture HOME's `.bun/bin/bun` fallback location (the exact location the
  pre-fix unconditional discovery loop would have silently substituted). Added
  `a handed-off Bun below the version floor fails closed instead of falling back to PATH discovery`
  to close it.
- Follow-up row: `scripts/sync-codex-installed-copies.sh`'s four `bun "$SOURCE_ROOT/..."` calls, the
  two `bunx` skill-installer calls in `global-runtime.ts` (Waza/Mermaid), and the update-path
  candidate child (whose env only gets `bindBunRuntimeEnv`'s `PATH`-prefix treatment, never
  `REPO_HARNESS_BUN_BIN`) are the same class of gap `b87c7f39` fixed for `install-agent-fleet.sh`,
  left unfixed here because they were out of this slice's scope. Recorded in `tasks/todos.md`
  instead of fixed silently, per the deferred-goal ledger contract in the root `CLAUDE.md`.
  `init.ts:766` and the standalone `sync:codex-installed` script have no validated-Bun variable in
  scope at all (unlike `global-runtime.ts`, `init.ts` never calls
  `resolveBunExecutable`/`ensureSupportedBunRuntime`), so wiring them the same way needs its own
  design rather than a mechanical copy of `b87c7f39`'s pattern.

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| Fix the sibling Bun-by-name call sites in this same slice | Rejected | Out of the dispatched scope; `init.ts`'s callers have no validated-Bun variable in scope, so the fix needs its own design, not a mechanical copy |
| Generate this plan/notes pair with `repo-harness run capture-plan --execute` | Rejected | `--execute` drives `plan-to-todo.sh`, which sets `.ai/harness/active-plan`/`active-worktree` and starts contract-worktree machinery for a plan whose work is already committed; hand-authoring following the 0.5.9 precedent's header format avoids misrepresenting already-done work as newly active |
| Leave `REPO_HARNESS_BUN_BIN` unset instead of `""` in the two isolated tests | Rejected | `undefined` would drop the key entirely and Node/Bun would still inherit it from `process.env` under the spread; an explicit empty string is required to override the spread, matching `tests/cli/fleet-offer-acquire.test.ts:215` |
