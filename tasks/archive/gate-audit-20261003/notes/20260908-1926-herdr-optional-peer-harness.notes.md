## Design Decisions

- The herdr probe lives in `writeGlobalContextFiles` (`src/cli/commands/init.ts`), not in `renderGlobalRules`: the render function stays pure over its inputs, and the machine property is read exactly once per init run. It is a fifth optional parameter (`probeHerdr`, default `Bun.which("herdr") !== null`) rather than a `GlobalContextOptions` field, so the options object stays plain CLI-derived data and existing callers are unchanged.
- The variant mechanism is line-exact `{{#IF HERDR}}` / `{{#IF NO_HERDR}}` / `{{/IF}}` markers in `assets/reference-configs/global-working-rules.md`, stripped by `selectPeerHarnessVariant`. Line-equality scanning (not a regex over the whole document) keeps the marker language from colliding with any prose the template may gain, and every marker line is dropped whichever branch wins, so the managed block never leaks template syntax.
- `check-agent-tooling.sh` gets `herdr` as `required=false` next to `tmux` in `runtime_capabilities`; the strict-readiness gate is untouched, so an absent herdr is reported without failing host readiness.

## Deviations From Plan Or Spec

- `docs/reference-configs/global-working-rules.md` is regenerated by `bun run sync:reference-configs` even though only `docs/reference-configs/external-tooling.md` is named in `allowed_paths`. It is the deterministic projection of the edited assets source and `tests/reference-configs-projection.test.ts` fails without it.

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| Probe inside `renderGlobalRules` vs. in `writeGlobalContextFiles` | Probe in `writeGlobalContextFiles` | One machine read per init run; the renderer stays deterministic over explicit inputs and is trivially testable both ways |
| Shell out to `check-agent-tooling.sh` for herdr status vs. `Bun.which` | `Bun.which` | The tooling report is a diagnostic surface, not an init dependency; spawning it during init would add a second authority and a process cost for one boolean |
