## Design Decisions

- The pin (`35e0fa1c`) is a pure `0.5.13` → `0.6.0` literal swap over the same file set as the
  0.5.13 pin (`1e18118a`): `package.json` + `bun.lock`, `ARCHCTX_REQUIRED_VERSION`,
  `REFACTOR_PROVIDER_VERSION`, generated policy defaults and their seeders, the AXR drivers, and
  version-bound test fixtures. No `0.5.13` remains outside archives, plans, deploy records and CHANGELOG.
- `archctx-contracts@0.6.0` reached the registry before `archctx@0.6.0`; the pin waited for both.
- No code change is needed. `archctx-contracts` differs only by version literals. The installed 0.6.0
  binary reports the same `projectionRequest` (`v1`), `architectureRefreshSignal` (`v1`) and
  capabilities (`v1`) identifiers repo-harness asserts. Across the bundles the only schema-identifier
  change is `accepted-committed-change` v1 → v2 (plus new `accepted-committed-change-plan/v1` and
  `changeset-model-transition/v1`); repo-harness references none of them.

## Deviations

- The 0.6.0 handshake reports `projectionResult` `v2` and `architectureDocs` renderer `v4`; repo-harness
  does not pin those two values exactly. Revisit if that validation is tightened.
- The bundle diff (~6k lines) was compared by schema identifiers and handshake, not read line by line.

## Open Questions

- AXR5 clean-room (`check:archctx-integration`) failed in this environment: building `arch-context`
  from source could not resolve `yaml`, so the build needs `bun install` in `../arch-context` first.
  It has not been re-run, so registry-vs-source equivalence for 0.6.0 is unverified.
