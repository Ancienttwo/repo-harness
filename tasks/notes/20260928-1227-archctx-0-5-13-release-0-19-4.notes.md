## Design Decisions

- The archctx/archctx-contracts pin (commit `1e18118a`) moves every pin surface from 0.5.12 to
  0.5.13: `package.json` + `bun.lock`, `ARCHCTX_REQUIRED_VERSION`
  (`src/core/architecture/projection.ts`), `REFACTOR_PROVIDER_VERSION`
  (`src/core/refactor/policy.ts`), the generated policy defaults (`.ai/harness/policy.json`,
  `scripts/ensure-task-workflow.sh` and its `assets/templates/helpers/ensure-task-workflow.sh`
  projection, `scripts/lib/project-init-lib.sh`), the AXR clean-room drivers
  (`scripts/axr5-archctx-clean-room.ts`, `scripts/axr6-stop-host-cycle.ts`,
  `scripts/axr7-consumer-e2e.ts`), and the version-bound test fixtures — the same 24-file
  inventory the 0.5.9 and 0.5.12 precedents enumerated; no new surface appeared. The diffstat
  (`24 files changed, 61 insertions(+), 61 deletions(-)`) is line-for-line identical to the 0.5.12
  pin's own diffstat, which is expected: both are a pure `s/<old>/<new>/g` version-literal swap over
  the same file set.
- `bun.lock` was regenerated by editing `package.json`'s two dependency literals to `0.5.13` and
  running `bun install` (not frozen, so Bun re-resolves the two bumped deps against the live
  registry) rather than hand-editing the lockfile's integrity hashes. The regenerated
  `sha512-` integrity strings were diffed byte-for-byte against `npm view archctx@0.5.13
  dist.integrity` and `npm view archctx-contracts@0.5.13 dist.integrity`: both match exactly. The
  registry's `dist.shasum` for both packages also matches the values the dispatching task supplied
  (`archctx`: `e35ba1bc3b53c6675eb133f0008a9b9e3d17e494`; `archctx-contracts`:
  `a2f089d2830e52679ed3985be5b10f7f4ee8397b`).
- Capability decision: 0.5.12 and 0.5.13 advertise identical capabilities, so
  `ARCHCTX_REQUIRED_FEATURES` (and `REFACTOR_SCAN_FEATURES`/`REFACTOR_VERIFY_FEATURES`) are
  unchanged — the same "no companion change" outcome the 0.5.12 pin recorded relative to 0.5.11.
  Verified by capturing `node node_modules/archctx/bin/archctx.mjs capabilities --json` once against
  the installed 0.5.12 baseline and once against 0.5.13 after the pin, then diffing the two JSON
  bodies with the version field normalized: identical (11 features:
  `architecture-docs-renderer-v2`, `architecture-refresh-signal-v1`, `module-statistics-v1`,
  `projection-apply-readback-v1`, `projection-apply-receipt-v1`, `projection-apply-recovery-v1`,
  `projection-prior-committed-applies-v1`, `projection-protocol-v2`, `recommendation-v3`,
  `refactor-assessment-v1`, `refactor-resolution-v1`). A real in-repo handshake after the pin
  (`bun src/cli/index.ts architecture-projection status --json`) reports
  `"version": "0.5.13"`, `"reason": "exact package-local capability handshake passed"`.
- Consumer-facing change check: archctx 0.5.13 changes invalid-RPC-input handling for its
  `developerReview.*` daemon methods (`startRun`, `attestation`, `cleanupRun`, `recoverRuns`,
  defined in `packages/local-runtime/runtime-daemon/src/developer-review-run.ts` inside the
  `archctx` package) from an HTTP 500 string to an HTTP 200 body carrying `AC_SCHEMA_INVALID`.
  Grepped repo-harness's `src/`, `tests/` and `scripts/` for `runtime-rpc-input-invalid` and
  `runtime-rpc-call-failed`: zero matches, both patterns. The one `AC_SCHEMA_INVALID` hit in current
  code (`src/cli/hook/mutation-observed.ts:101`, a comment) refers to archctx's existing
  non-retryable projection-journal rejection code, unrelated to the daemon RPC HTTP-status change.
  There is no `developer-review`/`developerReview` string anywhere in repo-harness's own source, and
  no daemon-RPC HTTP client of any kind (`archctxd`, unix-socket, or `fetch`-based) — repo-harness's
  only integration surface with archctx is the CLI subprocess handshake
  (`capabilities`/projection-request/projection-result/refactor scan/verify over stdio), which this
  RPC change does not touch. Nothing in repo-harness depends on the old HTTP 500 shape.
- The 0.19.4 release prep (commit `5375332c`) follows the 0.19.3 precedent's (`c9c54705`) exact
  9-file set: `package.json`, `assets/skill-version.json`, the five `README*.md` "Current Release"
  stamps, `docs/CHANGELOG.md`, and a new `deploy/release-checklists/260928-repo-harness-0.19.4.md`.
  Confirmed no other file references the old `0.19.3` version string outside historical/comment
  context (`docs/CHANGELOG.md`'s own `[0.19.3]` section header, and a code comment in
  `tests/installed-copy-sync.test.ts` referring to "pre-0.19.3" shell behavior — both correctly left
  alone), and `check:hooks`/`check:helpers`/`check:reference-configs` stayed clean after the bump, so
  no generated projection needed a companion regeneration.
- The changelog entry for 0.19.4 covers three things per the dispatch: the archctx 0.5.12 pin (#455,
  already merged) and 0.5.13 pin (this PR); the fleet Bun-handoff fail-closed fix from #455 (hands
  the runtime's validated Bun to the agent fleet installer via `REPO_HARNESS_BUN_BIN` instead of
  letting it re-discover `bun` by name, and fails closed when the handed-off Bun is below the
  version floor); and #455's new Bun-handoff regression coverage (isolated the two existing
  Bun-version tests from the invoking shell's own `REPO_HARNESS_BUN_BIN`, and added a new
  fail-closed-below-floor test). All three were already committed on `main` before this PR except
  the 0.5.13 pin itself.
- Release-checklist finding, not fixed here: `npm view repo-harness dist-tags.latest` still reports
  `0.19.2`. The `0.19.3` release was prepared (`c9c54705`) but was never published — this PR's
  `package.json` moves straight from the committed-but-unpublished `0.19.3` to `0.19.4`. Recorded
  plainly in `deploy/release-checklists/260928-repo-harness-0.19.4.md`'s header rather than glossed
  over; repairing the gap (publishing 0.19.3, or deciding it's superseded) is an orchestrator/owner
  decision outside this dispatch's scope.

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| Hand-edit `bun.lock`'s integrity hashes directly instead of running `bun install` | Rejected | `bun install` against the live registry is the canonical regeneration path and self-verifies against the exact bytes npm serves, rather than trusting a hand-copied string |
| Run the AXR5 clean-room check directly against the live `/Users/chris/Projects/arch-context` checkout (the script's own default `--arch-context-root`) | Rejected | That directory is the orchestrating session's own primary working directory; running `bun install --linker hoisted` there would change its `node_modules` layout as a side effect outside this task's authorized surface. A disposable clone at the same tagged commit (`aa93324`) gives identical evidence without that side effect |
| Commit the regenerated `docs/verification/axr5-archctx-clean-room-readback.json` alongside the pin | Rejected | Neither the 0.5.9 nor the 0.5.12 pin precedent touched this file; it is stale (last at 0.5.7) and updating it was not part of this dispatch's named file set. Reverted after use |
| Generate this plan/notes pair with `repo-harness run capture-plan --execute` | Rejected | `--execute` drives `plan-to-todo.sh`, which sets `.ai/harness/active-plan`/`active-worktree` and starts contract-worktree machinery for a plan whose work is already committed; hand-authoring following the 0.5.12 precedent's header format avoids misrepresenting already-done work as newly active |
