## Why

The two fixes merged after `v0.11.1` are verified on `main` but are not available
to npm consumers. A release prepared from any other source commit, or a tag
created before npm publication succeeds, would split package and source
authority across irreversible public surfaces.

## Goal

Publish `repo-harness@0.11.2` from one exact verified `main` commit, then bind
the npm package, annotated Git tag, and stable GitHub Release to that source and
prove the published package through registry, tarball, and clean-room install
readbacks.

## Scope

- In scope:
  - synchronize the package, skill/template stamp, five localized README
    projections, changelog, and dated release filing to `0.11.2`;
  - run focused, strict workflow, full local release, and hosted CI gates;
  - merge the release candidate, publish npm, push annotated `v0.11.2`, create
    the stable GitHub Release, and perform published-package readbacks;
  - close and archive the generated workflow artifacts after public truth is
    verified.
- Out of scope:
  - product/runtime behavior changes, dependency upgrades, context diet,
    current-snapshot policy, writer ownership, and telemetry semantics.
- Taste constraints: preserve the existing no-asset GitHub Release convention;
  npm is the package artifact authority. Add no release abstraction or fallback.

## Stop Conditions

- Stop and hand back to the parent if the change would require editing a path outside Allowed Paths.
- Stop if an Exit Criteria command cannot be run in this environment.
- Stop if Goal, Scope, or Exit Criteria are internally contradictory.
- Stop before tag/Release creation if npm authentication, publication, exact-main
  verification, or hosted CI fails.
- Stop after an ambiguous npm response and inspect registry state before retrying
  because published versions are immutable.

## Falsifier

If `0.11.2` already exists on npm, if either included commit requires a minor
compatibility boundary, or if version projections cannot pass the existing
consistency gate without product changes, this patch-release direction is
wrong. The cheapest proof is npm version-availability plus the exact
`v0.11.1..main` commit/file diff.

## Root Cause Evidence

Required when Task Profile is `bugfix`; leave as-is otherwise.

- root_cause: one sentence naming file:line/condition (testable, not "a state issue").
- repro: the command or UI path that reproduces the symptom.
- regression_guard: path to a test that fails on the unfixed code and passes after the fix (must also appear under exit_criteria.tests_pass).
- pre_fix_failure_artifact: path to a captured run of regression_guard on the UNFIXED code. Capture with `bun test <regression_guard> > <artifact> 2>&1; echo "PRE_FIX_EXIT=$?" >> <artifact>` (no pipes — pipes swallow the exit status). The gate requires a non-zero `PRE_FIX_EXIT=` line plus the regression_guard path string in the artifact (see the Root Cause Evidence Gate section in docs/reference-configs/sprint-contracts.md).
